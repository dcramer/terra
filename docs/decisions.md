# Decisions

The source of truth for what is settled. Other docs must agree with this one.

**Who decides:** design decisions (gameplay, art, scope, what the game is) belong to the developers. Technical decisions (engine, architecture, tooling, workflow) are made by the agent, recorded here with the reason, and can be overruled. The Owner column says which is which.

**Everything here is provisional.** This is pre-production: the whole record is our current thinking, written down so we can keep working from it, and any of it may change. The statuses say how firm an item is relative to the others, not that anything is locked.

**Decided**: our current answer; don't reopen without a reason. **Leaning**: working assumption, untested or unconfirmed. **Open**: not chosen. **Rejected**: considered and dropped.

| D25 | Performance target | Tech | Decided | 60 fps at 1080p on a mid-range discrete GPU and a 4-core CPU, as a client of a server holding a thousand players (D52), with dozens of them in view. The world must be able to show very many objects and let the player interact with any of them, and we look for ways to make that cheap everywhere. | Performance is a requirement. | D26 | Where the simulation runs | Tech | Decided | On its own thread, at a requested rate, never inside the render frame. The game takes a short lock to read or change it. | Running it inside the frame dropped the demo to 7 fps at x100. On a thread, x100 (6,000 ticks a second) costs the frame nothing. |
| D27 | Build in Rust instead of Godot | Design | Decided | Yes. | Decided by the developers on 2026-10-06, accepting that it costs weeks before the game is back to where the Godot demo is. |
| D28 | How the code is split | Tech | Decided | Anything that must be the same for every player lives in plain Rust crates that do not depend on Bevy (`terra_gen`, `terra_sim`, `terra_voxel`, `terra_core`, `terra_net`). | D29 | How state is shared | Tech | Decided | World changes are operations applied in the server's order (D21). The simulation runs only on the server and is sent as snapshots. | D30 | Maths in shared state | Tech | Decided | The `libm` crate for sine and similar functions, never the system maths library. | D34 | Networking library | Tech | Leaning | Our own messages over `renet`, with a Steam transport added later. No replication framework. | Our model needs only a reliable ordered channel and an unreliable one. Untested here. |
| D35 | UI | Tech | Leaning | Bevy's own UI for the game; `bevy_egui` for developer tools. | Untested here. Bevy's UI is younger than Godot's; reassess when the game needs real menus. |
| D36 | Coordinates | Tech | Leaning | One coordinate frame per world, with positions relative to an origin that moves with the player, and 64-bit positions on the server.
