# D413: A push's check runs again only what a rebase changed, and at most two build and test at once

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

When the check before a push passes on a commit's tree (no tracked file changed), it stamps that tree in the worktree's own git folder (`terra-check-stamp`, `xtask/src/stamp.rs`). The next push's check scopes as before (everything differing from the merge-base with origin/main, D398) and also scopes what changed since the stamped tree; a package is linted and tested, and a scoped stage (kits, artifacts, fuzz, foliage, Blender, the manifests' rule) runs, only if both scopes hold it. So after `git pull --rebase` over others' commits it runs only what the push touches and the rebase changed, and over unrelated commits builds and tests nothing. The cheap stages (formatting, sizes, one definition, the tools' tests, docs, the repeatable rule) always run. A change to the check's own code since the stamp (`xtask/src/`, its manifest; not its baselines), a missing or unreadable stamp, or one naming a tree git no longer has narrows nothing; `--all` is never narrowed.

A push check that builds or tests anything first takes one of two machine-wide slots (`~/.cache/terra/check.slot-<n>`, advisory locks as D319's, `TERRA_CHECK_SLOTS` to change how many, `xtask/src/slot.rs`), saying it waits and which checkouts hold them; a check with nothing heavy, the quick check before a commit and every other task never wait.

The stamp is sound under the gate's own premise, that main passed: a stage's result depends only on what it reads, so one whose inputs are as stamped passed on them (or, left out of the stamped check, read what main holds); one whose inputs changed runs. The push still never skips its hook (D37) and still checks what lands against what it lands on.

## Measured

On the 10-core, 32 GB machine every session shares, other agents building and rendering (load average in brackets):

| | Before | After |
|---|---|---|
| Pre-push checks, four at once (2026-10-18) | 54, 60 and 80 min each [40-76], swapping 5.8 GB; the same `--all` push alone took 5m 41s (D406) | at most two build and test at once; the rest wait |
| A push refused because main moved during its check | 3 to 5 commits landed meanwhile; each retry ran the whole check again (the smoothstep cleanup twice, the incremental release builds once, the baselines change twice) | MEASURED_RETRY |
| This change's own push (xtask: its tests, kits, artifacts, fuzz) | MEASURED_FULL | — |

## Why

The developers' agents all push straight to main through the local hooks (D37, D375); under load a push's check took most of an hour and lost the race for main to whoever pushed meanwhile, so the same check ran again and again. A merge queue or a lock held over the whole check would serialise hour-long checks; a stamp makes the retry cost what the rebase brought, and the slots make the first run shorter instead of every check at a quarter speed.
