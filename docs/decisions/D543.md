# D543: GPU memory comes from the driver in blocks of 64 MiB

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

wgpu's allocator (gpu-allocator) takes device memory from the driver in blocks of 64 MiB, host memory (what uploads are staged in) in blocks of 32, not wgpu's default of 128 then 256 MiB (`MemoryHints::Manual`, `headless::MEMORY_BLOCK`). Each block is a `vkAllocateMemory` the driver clears before handing it over, in the frame whatever overflowed the last block asked, while the allocator's lock holds every other buffer made meanwhile. A 64 MiB block is a full mesh slab's page (D420). VMA, the allocator Godot's Vulkan driver uses, likewise begins with blocks an eighth of its 256 MiB default, growing them only as a heap fills.

## Why

Castle's worst frame (17.7 ms in two runs of three, frame 618, after D541) was the render world's `allocate_and_free_meshes` taking 12 to 14 ms to put a mesh of 11 to 23 MiB into a slab that grew. A probe timing `create_buffer` in the render world on the Radeon 8060S (RADV): a buffer that fits a block's free room costs nothing; one that needs a new block costs 40 µs a MiB of the block, 2.5 ms for 64 MiB, 4.9 for 128, 9.6 to 10 for the default 256. The sea's material, prepared again every frame the camera moves (`planet::sea::sea_waves`), took 10 ms in that frame only because it waited for the allocator beside it; it takes 0.1 to 0.2 ms otherwise, so it is left as it is.

`cargo xtask gpu bench -- cargo xtask bench castle town300 going-up world`, three quiet runs each, at aa7e8a44 and with this: `castle` worst 9.0, 17.7, 17.7 ms to 11.4, 11.4, 10.9 (the slowest left is a 23 MiB building section going up with its slab's growth, 7 ms of allocator), median 4.92 to 4.78, 99th percentile 7.95 to 7.87; `going-up` 4.31 to 4.38 ms, worst 18.7 to 16.2; `town300` 5.47 to 5.60 and `world` 7.26 to 7.43, which a second pair of benches of the two, after and before in turn, put at 5.44 against 5.47 and 7.33 against 7.41: the spread between sessions, not this.
