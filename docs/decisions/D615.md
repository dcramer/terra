# D615: The aerial-view table is drawn a workgroup a column

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

Bevy 0.20's `aerial_view_lut.wesl` runs a thread a column of the aerial-view table (32x32 threads, four workgroups on a card of over a hundred multiprocessors), each marching every slice's samples in a row, latency-bound on the table reads of every sample. It is now drawn a workgroup of 64 threads a column: the threads work out 160 samples at a time as `main` does (each sample's distance and step from the previous one, its extinction, transmittance and in-scattering, the whole chain in one thread), into workgroup arrays (10 KB); then lane 0 accumulates them in order exactly as `main` does (the throughput, the stop under 0.001 until the slice ends, the slice's store), as volumetric fog splits its per-froxel scattering from its accumulation along depth (Wronski, "Volumetric Fog", SIGGRAPH 2014). The same samples are taken in the same order, so the table holds the same texels to a rounding. A patch of `bevy_pbr` 0.20.0 (D184), marked `Terra's patch (D615)`:

- `atmosphere/aerial_view_lut.wesl`: the entry point `main_spread` beside Bevy's `main`, unchanged.
- `atmosphere/resources.rs`: the `aerial_view_lut_spread` pipeline; Bevy's names its entry `main`, the module now holding two.
- `atmosphere/node.rs`: dispatches a workgroup a column (`spread_aerial::spread_workgroups`) when `SPREAD_AERIAL_VIEW_LUT` is set and the pipeline is compiled, Bevy's 16x16 groups otherwise.
- `atmosphere/spread_aerial.rs`: the static and the dispatch size.
- The tunable `render.spread_aerial_view_lut` (`terra_world::air`, default 1) sets the static each frame; at 0 the table is drawn Bevy's way, so a probe measures the one against the other in one load (D609).

Variant A, where the threads kept only extinction and in-scattering and lane 0 did the steps and exponentials, moved 158,557 pixels of the lake's trees view (2,859 by more than one level), since the compiler orders the arithmetic differently across threads: rejected. Unreal's SkyAtmosphere and Hillaire's reference (`RenderCameraVolumePS`) run a thread a froxel, each marching from the camera to its own slice with its own samples: fully parallel, but other samples, so another look.

Upstream: Bevy's main has the same thread-a-column `main`. Not yet offered.

## Why

At the lake's route view (1901x1550, the worker's 4090), thread against spread in one load, three loads (job 20261103-205005-e093-patch): `atmosphere_luts` 0.153 -> 0.079 ms each load, TOTAL 7.032 -> 6.936, 7.088 -> 6.983, 7.007 -> 6.938 ms (A/A 0.009-0.030), the spread under the 7 ms of goal 1(c) in all three. Lake-play's bench at 1920x1080 with it on (job 20261103-212021-682c-patch): 8.75 ms (runs 8.66-8.85, `atmosphere_luts` 0.08), against D613's 8.91 and 8.81, holding D25. It draws the same: against the thread-a-column table, the trees view moves 774 pixels, 8 by more than one level, under the A/A's 5,883; the lake's other views, the tundra's three and the route's are within their own A/A (job 20261103-202335-1f93-patch, play-lake-fps j19), with no shader error. Tests: `spread_aerial`'s two (a workgroup a column; the workgroup arrays fit 16 KiB and the group is `SPREAD_THREADS` wide).
