# D581: `make play` runs the release build

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

`cargo xtask play` (`make play`, `yard`) builds and runs the sandbox in the release profile, not the dev one: on Windows from WSL the release Windows build, elsewhere `cargo run --release`. Our crates build incrementally in release (D408), so a launch after an edit compiles only what changed, and the seed holds the Windows release build. What the dev profile alone gave play is lost: overflow checks, `debug_assert!`s and Bevy's `track_location`; a bug that needs them is chased with `cargo xtask win -p terra_sandbox -- --experiment play`.

## Measured

RTX 5090, 9950X3D, the developer's save, offscreen bench of 4,000 frames walking 0,-150 150,-150 150,0, textures cooked (D188), two runs each:

| | Debug (dev profile) | Release |
|---|---|---|
| Loaded in | 25.1 s, 22.1 s | 15.0 s, 13.7 s |
| Frame median / 99th / worst (ms) | 13.5 / 21.2 / 65; 13.3 / 20.1 / 62 | 10.2 / 14.8 / 32; 10.3 / 14.9 / 32 |
| The game's work, median (ms) | 11.7; 11.6 | 8.7; 8.7 |
| Frames over 500 ms | 0; 0 | 0; 0 |

The developer's 1 to 3 s freezes in play are not on this route in either build (none over 100 ms); they are chased apart (perf round 3).

## Why

The developer found `make play` slow to load (25 to 30 s) and freezing every 10 to 20 s (perf round 1). The debug build builds our crates at opt-level 1, which costs the main thread a third more each frame and the load 7 to 10 s. Shipped engines play-test an optimised build (Unreal's Development configuration) and keep the unoptimised one for the debugger.
