# D563: The character build is incremental, a stamp a step

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

`build_bodies.sh` runs its steps as make and ninja run theirs (`tools/characters/build.ts`, the steps as data in `build_steps.ts`). Each step's stamp is the hash of what it reads: its scripts with the local modules they import and the data those read, its art, its command, and the outputs of the steps it needs. A step whose stamp holds and whose outputs are as it left them is skipped; a changed one runs, and so does what reads its outputs, unless they come out the same (ninja's restat). A step killed part-way has no stamp, so a rerun resumes. A look is fitted on each body (carried, pushed clear in three rounds, checked) as a step of its own, so a change to one garment rebuilds that garment on every body and its game file, not every look. `build_item.sh` is the same build aimed at one item's game file.

A committed file a step rewrites in place whose rewrite is not idempotent (the mannequin: Blender's glTF round trip in `made_clips.py` moves its floats a little each time) is taken as built while git has it and every input of its step as committed; the step then checks without rewriting. So a cold build on a clean checkout reproduces main's files rather than drifting from them.

## Why

The developers' priority, "to minimize token waste, to improve incremental reliability": the all-or-nothing build took 1.5 to 2 hours, three jobs in a week ran out of context waiting on it, and session restarts killed two mid-build, losing everything. Stamps from content hashes (not file times) survive git checkouts and worktree copies; a step a look on a body matches what `build_item.sh` already did and costs a Blender start a step. The verdict is read from the steps' kept logs in the build's order, so a skipped step's checks still count; the only change to `build_verdict.ts` is that it counts a check a look a body (bodies times looks) where it counted one a body.
