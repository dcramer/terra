# D548: What changed this? Bevy's track_location in dev builds, asked over the remote

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

The sandbox's dev builds are built with Bevy's `track_location` feature (`terra_sandbox`'s `track_location`), so Bevy keeps the place in the source of every spawn and of the last insert or mutable borrow of every component; release and bench builds never are, so nothing timed or shipped carries it. The remote answers `sandbox.why {entity, component?}` (`r why ENTITY [COMPONENT]`, `crates/terra_world/src/remote/why.rs`): who spawned the entity and, for each component, the file and line that last changed it, the function it is in (for a system, the system), and on which frame and how many frames ago. Bevy stamps a change with a tick, which counts system runs, not frames, so the remote keeps the tick each frame began on, for the last ten minutes, and tells a tick as the frame it fell in. It is the data breakpoint's question (Visual Studio's, gdb's watchpoints) asked after the fact, as Godot's remote inspector, Unity's and Unreal's debuggers let a person look into a running game; ours is for agents as much as people (D69).

Only a dev build has the feature, and Cargo cannot set a feature by profile, so it is passed where a dev sandbox is built: xtask's `sandbox`, `workbench`, `play` and `win` (`tasks::sandbox::dev_features`), the remote's `start` without `--release`, and the seed, so the dev build is linked, not built again in each worktree (D183). A dev build of the sandbox is therefore a second build of Bevy beside the tests' (Cargo builds a crate again for each set of features), made once in the seed. Without the feature, `why` still gives each change's frame and says the lines are not kept.

A body drawn between fixed ticks (`tick::Smoothed`, D138) has its `Transform` written last, each frame, by that drawing (`tick.rs`'s `show`), so the line that answers is never what moved it. Engines with interpolated physics keep the drawn transform apart from the simulated one (Unity's Rigidbody `position` beside its interpolated `Transform`, Unreal's physics body beside its smoothed mesh), and so does `Smoothed`: it keeps the last change to where the body truly stands made by anything but `tick.rs` (which stands it back where it truly is at each tick's start and draws it between), with its line, its change tick and whether a tick made it or something outside the ticks did (a teleport). A tick's system that writes the place a body already stands in (as the walker's `walk` does for a standing player, each tick) changed the component but did not move it, so it is not counted. `why` tells it beside the last write for any smoothed body: `Transform  crates/terra_world/src/tick.rs:166 in show, frame 486, 33 frames ago; drawn between ticks, last moved outside the ticks by crates/terra_walker/src/walker.rs:512 in warp, frame 484, 35 frames ago`. `tools/sandbox/whycheck.ts --windows` proves it in play on the Windows dev build: it fails on main (2026-10-27, why named only the last write) and passes with this.

A component that cannot change (an immutable component, as `ChildOf`) gives no line: Bevy hands out a change's place without `unsafe` only through a mutable borrow, which such a component refuses (D: no `unsafe`).

## Why

The brief (2026-10-27): "answer 'what changed this?' over the sandbox remote"; `track_location` "on in dev and remote sandbox builds only; never in release or the bench profile (bench numbers must not move)". A bug of the kind "something moves the player back" or "who keeps resetting this" was found by reading code or bisecting; now one call names the line.

The bench build's features are unchanged: `cargo tree -p terra_sandbox -i bevy_ecs -e normal`, which `cargo xtask bench`'s `build --profile bench -p terra_sandbox` builds, gives bevy_ecs `async_executor, backtrace, bevy_reflect, default, multi_threaded, reflect_auto_register, serialize, std`; `track_location` appears only with `--features track_location`.

By Bevy's design it costs a pointer (8 bytes) per component per entity and a store on every mutable borrow, and nothing at all where the feature is off. Measured on the Windows dev build (2026-10-27), the play experiment fresh at the start, 30 s in, then 10 s of `sandbox.frames` and the process's memory, once with the feature and twice without: the game's median frame work 15.2 ms with it, 15.5 and 69.7 ms without; working set 4.81 GB with it, 4.72 and 4.84 GB without; private memory 11.14 GB with, 11.13 and 11.27 GB without. The difference is inside the run-to-run spread: every run was on a machine other agents held at 88-95% CPU (it never went quiet in 300 s), so a smaller cost than the spread is not ruled out, only a large one. Release and bench builds, which are timed, never have it.

The next tool is Bevy's `bevy_debug_stepping` (its `Stepping` resource) over the remote: stop the schedules and run systems one at a time, so an agent sees a change as it is made rather than after the fact. Not built.
