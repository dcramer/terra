# D445: Renders run on a GPU box that takes jobs over SSH

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Leaning

An agent's heavy render (a trailer cut or its stills, a sheet, a bench, a scripted offscreen shot) can run on a second machine with a bigger card: `cargo xtask remote-render [--rev <sha>] -- <command>` pushes the commit straight to the box's own clone over git+ssh as `refs/jobs/<id>`, queues the job with a small daemon there, waits on it over ssh while the box watches the job (no polling across the network), and rsyncs what the command wrote under `~/.cache/terra-review/` (or `--collect` paths) into `~/.cache/terra-review/remote/<job>/` ([docs/render-worker.md](../render-worker.md), [tools/render-worker](../../tools/render-worker/README.md)). The daemon is a systemd user service with lingering (a detached supervisor where that is not allowed), runs natively, not in Docker, `TERRA_RENDER_SLOTS` (4) jobs side by side, each in a slot with its own worktree checkout, `target/` and HOME so builds never lock each other, of them at most `TERRA_RENDER_GPU_SLOTS` (3) GPU jobs (a job's class from its command, or `--gpu`/`--cpu`) and a bench alone on the box, within an optional window of hours, and listens on no port: ssh is the only way in. `--update` pushes origin/main to the box, which checks itself out at it, tries the new daemon and goes back if it fails, restarts, and rebuilds the sandbox and clippy's cache in every slot in the background, so an agent repairs the worker without the developer visiting. `--doctor` checks the GPU, Vulkan, Node, cargo, the build libraries, disk and the daemon. Settings are in `.env` (`.env.example`): `TERRA_WORKERS`, a comma list of ssh hosts, on the client; the window and the rest in the `.env` of the box's clone. With `TERRA_REMOTE_CHECKS=1` the push hook runs its check (`cargo xtask check --base <merge-base>`) on the worker at each commit pushed instead of locally, failing the push when it fails or the worker is unreachable (`tools/git/remote-check.ts`).

## Why

The developers, 2026-10-23: "when you wanna record a video, you push code, queue it with that docker image, what revision it has to run, what it has to run etc. and it will give you back an actual file link or something/artifacts". Rounds lose most of their time waiting for the one 10 GB card (D319). On 2026-10-24 they set the transport: "configs should go to env. you can set that up. WORKERS can be a list or just a specific host" and "im happy to set up a worker, but i wont do github yet, so no token needed, i just need to open up a server so you can start querying and debugging. ideally we also need a process that lets you self update that so i dont have to go there and fix it up every now and then". So the first shape, draft GitHub releases as the queue and file store with a token on the box, went: ssh already gives the access control (whoever can log in), the transport (git push, rsync) and a way to debug, with nothing open on the network. Native over Docker because the box already has cargo, Docker would need the NVIDIA Container Toolkit (sudo) and Vulkan inside a container, and an update is a checkout and a restart rather than an image build; the job runs as the user either way. On 2026-10-24 the developers: "that computer is much more beefy so you don't have to queue everything, you can run a lot in parallel": the box has 32 cores, 125 GB and a 24 GB RTX 4090, which holds about three films at 7 GB each, so jobs run in slots; a bench keeps the box alone because a build beside it moves its frame times (D185). The same day all building moved off the developer's machine (an embargo), so the push hook's checks may run on the worker. Leaning until a GPU job has run on the box.
