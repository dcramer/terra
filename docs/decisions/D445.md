# D445: Renders run on a GPU box that takes jobs over SSH

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Leaning

An agent's heavy render (a trailer cut or its stills, a sheet, a bench, a scripted offscreen shot) can run on a second machine with a bigger card: `cargo xtask remote-render [--rev <sha>] -- <command>` pushes the commit straight to the box's own clone over git+ssh as `refs/jobs/<id>`, queues the job with a small daemon there, waits on it over ssh while the box watches the job (no polling across the network), and rsyncs what the command wrote under `~/.cache/terra-review/` (or `--collect` paths) into `~/.cache/terra-review/remote/<job>/` ([docs/render-worker.md](../render-worker.md), [tools/render-worker](../../tools/render-worker/README.md)). The daemon is a systemd user service with lingering (a detached supervisor where that is not allowed), runs natively, not in Docker, `TERRA_RENDER_SLOTS` (4) jobs side by side, each in a slot with its own worktree checkout, `target/` and HOME so builds never lock each other, of them at most `TERRA_RENDER_GPU_SLOTS` (3) GPU jobs (a job's class from its command, or `--gpu`/`--cpu`) and a bench alone on the box for its timed run (its checkout, cook and the builds its command starts with done ahead in a slot of its own while the box drains, the same binary built; the first queued bench waits `TERRA_RENDER_BENCH_WAIT` (30) minutes for the box to empty on its own, every job starting as usual and the bench building in a slot nobody wants, before it drains the box; while the box drains for one, a job behind it starts only if the last of its kind would end before the running jobs likely do (a running job as long again as it has run, by its limit; a new kind as long as its limit), and on the empty box queued benches run back to back when that costs less waiting than another drain; the push hook's check never waits on the queue, as CI farms keep runners for a fast lane: it goes ahead of every job but the warm builds, into a check slot past the job slots that nothing else takes (`TERRA_RENDER_CHECK_SLOTS`, 1) or else any free slot, whatever its length while the box drains, a built bench going once no check runs or waits, but never beside the timed run; a bench's script of several timed runs stops at a gate before each `cargo xtask bench`, where only queued checks start and from which it goes on once none runs, so each timed run still has the box alone), within an optional window of hours, and listens on no port: ssh is the only way in. `--update` pushes origin/main to the box, which checks itself out at it, tries the new daemon and goes back if it fails, restarts (once no job runs, starting only checks meanwhile), and rebuilds the sandbox and clippy's cache in every slot in the background, so an agent repairs the worker without the developer visiting. A job that draws (a GPU job, a bench, any sandbox run) gets a display, since winit's event loop needs one even offscreen: `TERRA_RENDER_DISPLAY`, else the daemon's own, else one Xvfb the daemon starts on a free number, keeps for its lifetime, restarts if it dies and stops on exit; the NVIDIA driver renders headless under Vulkan. `--doctor` checks the GPU, Vulkan, the display, Node, cargo, the build libraries, disk and the daemon. The daemon guards its disk as CI agents do: before each job, under a low mark (the larger of 15% and 150 GB) it prunes idle slots' debug incremental, then old jobs' collected files, then idle slots' release incremental; a full disk (under 30 GB after pruning, or any ENOSPC) is caught, never crashed on, and starts no job; `--status` and every client wait say at once when the daemon is down or the disk full, with the fix ([the disk](../render-worker.md#the-disk); 2026-10-30's full disk crash-looped it unnoticed for 63 hours). Settings are in `.env` (`.env.example`): `TERRA_WORKERS`, a comma list of ssh hosts, on the client; the window and the rest in the `.env` of the box's clone. With `TERRA_REMOTE_CHECKS=1` the push hook runs its check (`cargo xtask check --base <merge-base>`) on the worker at each commit pushed instead of locally, failing the push when it fails or the worker is unreachable (`tools/git/remote-check.ts`); a pass is kept, and a push rebased after losing its race reuses it, as a merge queue reasons, when its commits' patch-ids are unchanged and main's new commits touch none of its files, no crate related to its crates by dependency either way, no file every check reads (Cargo files, toolchain, lint settings, `xtask/`, `patches/`) and no file a crate's code includes, Markdown outside the crates and xtask, which the check never reads, left out of both patches and overlap; anything it cannot tell checks again (`tools/git/check-reuse.ts`, `TERRA_RECHECK=1`).

## Why

The developers, 2026-10-23: "when you wanna record a video, you push code, queue it with that docker image, what revision it has to run, what it has to run etc. and it will give you back an actual file link or something/artifacts". Rounds lose most of their time waiting for the one 10 GB card (D319). On 2026-10-24 they set the transport: "configs should go to env. you can set that up. WORKERS can be a list or just a specific host" and "im happy to set up a worker, but i wont do github yet, so no token needed, i just need to open up a server so you can start querying and debugging. ideally we also need a process that lets you self update that so i dont have to go there and fix it up every now and then". So the first shape, draft GitHub releases as the queue and file store with a token on the box, went: ssh already gives the access control (whoever can log in), the transport (git push, rsync) and a way to debug, with nothing open on the network. Native over Docker because the box already has cargo, Docker would need the NVIDIA Container Toolkit (sudo) and Vulkan inside a container, and an update is a checkout and a restart rather than an image build; the job runs as the user either way. On 2026-10-24 the developers: "that computer is much more beefy so you don't have to queue everything, you can run a lot in parallel": the box has 32 cores, 125 GB and a 24 GB RTX 4090, which holds about three films at 7 GB each, so jobs run in slots; a bench keeps the box alone because a build beside it moves its frame times (D185). On 2026-10-28 benches cost rounds 1 to 2 hours each, the box idle while it drained; replaying the box's queue of 27-28 October (1,156 jobs, 25 benches) under each rule, filling the drain with jobs that end in time cut all jobs' waiting from 143 to 123 hours (CPU jobs' from 33 to 15) and the benches' a little, with no bench ever beside a job. Running every queued bench back to back regardless made the waiting worse (154 hours): a bench's own run, 5 to 40 minutes alone, then holds every job queued between, and today's five benches would have held the box for 2 h 15. Two crypt benches run back to back on one commit measured alike (medians 8.84/8.77/8.83 ms after a drain, 8.78/8.80/8.94 ms straight after the other). Benches then held the box alone 6.2 hours in two days with jobs waiting, and each spent 20 s to 1 min 15 s of it building the sandbox and cooking, which needs no quiet box and moves no frame time (the binary is the one the bench would build itself), so a bench builds in a slot while the box drains and has it alone only for the timed run. The same day all building moved off the developer's machine (an embargo), so the push hook's checks may run on the worker. On 2026-10-29 pushes waited 45 to 60 minutes on their check behind benches: a drain the estimates called "any moment" while a render ran on for two hours, then the timed run. A check beside the timed run was measured first (job 20261029-170216-7e58-patch, crypt, 600 frames): one cold `cargo xtask check` pinned to the efficiency cores 16-31 under `ionice -c 2 -n 7 nice -n 19` (they were 94% busy, 0-15 as alone) moved the median from 8.87 and 8.90 ms alone to 11.26 and 11.27 ms, 99th percentile 13.16 and 12.91 to 16.12 and 15.81 ms, the game's own work 8.05 to 10.05 ms: the performance cores slow when the others work (shared ring, power), so nothing runs beside a timed bench. A check takes about two minutes (113 and 114 s cold on 16-31), so it starts during the drain while a job other than a check still runs, and holds the bench back by at most its own length. On 2026-11-02 a bench queued at 09:40 held its slot built for 49 minutes while the one 55-minute render ran, the other three slots idle: the drain took "any moment" for a running job past its kind's shortest run or of a kind never run, so nothing behind it fitted, and GPU jobs queued behind waited 133 to 148 minutes, a one-second CPU job 172. Replaying the box's real queue (26-29 October, and 1 November 12:00 to 2 November 12:40) with each job's real run time: a running job likely runs as long again as it has (job lengths are heavy-tailed, Harchol-Balter and Downey 1997) and a new kind counts as its limit (as Slurm's backfill does); with that, a bench that first waits 30 minutes for the box to empty on its own cut all jobs' waiting from 151.9 to 139.7 hours and from 37.1 to 22.5 (GPU jobs' 23.4 to 8.4), the benches' rising from 4.0 to 6.4 and 7.9 to 8.6 hours, and no job ever beside a timed run; a 15-minute wait gained less (137.2 and 53.0), 60 minutes a little more on one window and less on the other, a cap on how long jobs may hold a bench back was worse (155 and 40), and draining at once for an unbuilt bench on an empty box worse too (143.2 and 24.7). The same day every agent's push lost two or three races: of 45 push checks, 20 waited over a minute to start (p90 30 minutes, the longest 53) while each ran for a minute or two (p90 1.3), main moved meanwhile, and the rebased push ran its check again. Nine waited on a bench's timed run; the other eleven on all four slots taken (three renders and a test, or the warm builds after an update) or on a built bench held for the drain. So checks get a slot of their own and the head of the queue, as CI farms keep a pool for fast lanes; the timed run still has the box alone. And a lost race need not cost a check: the hook's check is a function of the files a push changes (formatting, sizes, one definition, file by file) and the crates they are in with their dependencies and dependents (clippy), so the same patches over a main whose new commits touch none of those, nor what every check reads, give the same result, as Uber's SubmitQueue ("Keeping master green at scale", EuroSys 2019) treats changes whose build targets do not overlap as independent; a re-check would only wait again behind the same queue. The first real race (17:04 the same day) showed patch-ids of whole commits never match after a rebase here: nearly every push appends to docs/decisions-log.md, whose hunk's context then changes, so Markdown the check never reads is left out. A daemon waiting to restart on new code started nothing, checks included, until its running jobs ended: an update at 17:07 on 2026-11-02 beside three 35-53-minute renders froze every push for 36 minutes, where a check is a minute or two and the restart waits for whatever runs anyway. The same day 12 of 45 checks waited out timed benches, lakeperf's A/B scripts holding the box 20 to 60 minutes for several `cargo xtask bench` runs in one job; as benchmark harnesses part trials (hyperfine's `--prepare`, JMH's forks), a check runs in the gap between two runs and the next starts only once it ends and the bench's own wait for a quiet machine passes. Leaning until a GPU job has run on the box. The display: on 2026-10-24 every sandbox job on the box panicked "neither WAYLAND_DISPLAY nor DISPLAY is set", since nobody is logged into its desktop and the user service has no display; an Xvfb the daemon owns needs no login and no sudo, and a real display can still be named.
