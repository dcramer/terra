# D613: Bin unpacking and uniform allocation run once a view, phase and mesh class, not once a batch set

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

Bevy 0.20's GPU preprocessing ran its bookkeeping shaders, `unpack_bins` and `allocate_uniforms` (a local scan, a global scan and a fan), once for every multidrawn batch set of every view and phase, each dispatch with buffers and a bind group of its own: about 146 small dispatches a frame at the lake, most of them idle waiting on the one before. They now run once for every non-empty (view, phase, mesh class), as GPU-driven renderers do (Wihlidal, "Optimizing the Graphics Pipeline with Compute", GDC 2016; Haar and Aaltonen, "GPU-Driven Rendering Pipelines", SIGGRAPH 2015): one dispatch over every draw, each thread finding its batch set's record in a table of offsets. A patch of `bevy_render` and `bevy_pbr` 0.20.0 (D184), marked `Terra's patch (D613)`:

- `bevy_render`'s `batching/merged_unpacking.rs`: `MergedBinBuffers` lays a (view, phase, mesh class)'s batch sets end to end (their binned instances, bin metadata and bin-index map, and a fan buffer of their chunks). A dirty batch set is written in place while the layout (each batch set's `id` and lengths) is unchanged, so D583's writes stay few; otherwise the buffers are written whole. `plan` makes each batch set's `GpuBinUnpackingJob` and `GpuUniformAllocationJob`, two frame-wide storage tables in `SceneUnpackingBuffers`; the per-dispatch uniforms hold the first job, the job count and the total instances or chunks. `RenderMultidrawableBatchSetGpuBuffers::id` tells batch sets apart from frame to frame.
- `bevy_pbr`'s shaders: `unpack_bins.wesl` finds a thread's job by binary search on its instance start; `allocate_uniforms.wesl`'s local scan and fan find their (job, chunk) by first chunk through `workgroupUniformLoad` (naga treats a local as non-uniform before a barrier), and its global scan runs one workgroup a job; the global scan and fan are dispatched only when some job has more than 256 bins.
- The tunable `render.merged_unpacking` (`terra_world::gpu_bookkeeping`, default 1) sets the static `MERGE_SCENE_UNPACKING` each frame; at 0 every batch set gets its own `MergedBinBuffers`, Bevy 0.20's dispatch count, so a probe measures the one against the other in one load (D609).

Upstream: Bevy's main still dispatches once a batch set (the same `unpack_bins.wesl`, 2026-11-03); related open issues #26257 (bind groups made again every frame) and #26273. Not yet offered.

## Why

At the lake's route view (1901x1550, the worker's 4090) the two bookkeeping passes cost 0.69 ms of a 7.7 ms frame for work of a few microseconds: `uniform_allocation` 0.38-0.40 ms and `bin_unpacking` 0.30-0.31 ms, almost all of it the gaps between dependent dispatches. Merged they cost 0.018 and 0.012 ms, and the frame's GPU median falls by 0.64-0.70 ms, split against merged in one load, three loads (job 20261103-182806-0c64-patch): 7.72 -> 7.08, 7.74 -> 7.10, 7.81 -> 7.14 ms. It draws the same: the lake's three views, the tundra's three and the route's, merged, split and main's code shot twice, differ from main no more than main's two shots differ from each other (mean 0.03-0.17 a channel, the same pixels moving; job 20261103-180230-8189-patch), and no shader fails to compile. The bench at 1920x1080 (job 20261103-184235-4cc0-patch, three runs, against main's 1af588094 in job 20261103-174655-e980, one run): lake-play 9.57 -> 8.91 ms, forest-run 8.76 -> 7.76, town-dusk 9.27 -> 9.24, every 99th within D25; `bin_unpacking` at 0.01 ms falls out of the costliest 20 passes, so its budgets go (`assets/data/perf/budgets.ron`).
