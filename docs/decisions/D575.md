# D575: The launcher is a menu in the terminal, in `cargo xtask play`

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

`make play` opens a launcher: when `cargo xtask play` runs in a terminal with no choice on its command line, it shows one screen with what to play (continue, new game, creative, the yard) and the options (build debug or optimised, quality preset, profiling off, report or Tracy), the last launch preselected so Enter plays it again, remembered in `~/.config/terra/launch.json`. Every choice is also a flag, and a command line with any choice, or no terminal, skips the menu and takes the defaults, never the remembered launch (`--last` asks for it), so scripts and agents drive it (D69). After Unreal's launch profiles and UnrealGameSync. The launcher is a menu over `play`'s own path, so it builds on whatever that path does about cooking and the build (D188). [launcher.md](../launcher.md#the-launcher-d575). Built 2026-10-29 (`xtask/src/launcher.rs`), without the profiling option until the session report and Tracy land; a new game is remembered as Continue, so playing the last launch again keeps the world it made, and only the menu asks before a new game deletes the save (a flag is already a choice made).

## Why

The developer, 2026-10-29: `make play` should open a launcher "a normal person" can use, remember the last choice and be fully drivable by flags. The build's choices (debug or optimised, a Tracy build) must be made before Cargo runs, and under WSL builds run in Linux while the game runs in Windows: xtask already builds, cooks, stages and starts the copy, so the menu lives there. A native window would need a bridge from Windows back into WSL and a second program for macOS and Linux; the game's own screen is too late for the build's choices. The player's choices move to the game's front screen if the developers want one (D579).
