# D410: Tasks register from their own modules

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

Each xtask module that owns tasks lists them in its own `pub(crate) const TASKS: &[Task]` (`check.rs`, `sizes.rs`, `build.rs`, `bench.rs`, `doctor.rs`, `seed.rs`, `worktrees.rs`, `windows.rs`); a task that only starts a tool kept elsewhere (a TypeScript tool, a crate's program, a Blender or shell script) is listed in a module of `xtask/src/tasks/` by its area (`play`, `world`, `sandbox`, `art`, `docs`). `xtask/src/main.rs` keeps only `MODULES`, the list of those tables, and `GROUPS`, the order `cargo xtask tools` lists its groups in; within a group tasks keep the order of `MODULES` and of each table. Adding or rewording a task touches only its module. A test holds every name unique and every group listed across all modules, and the docs check reads task names from every `Task { name: "…"` under `xtask/src/` (D396). With it the material bench's task is `cargo xtask material` (tools/kits/material.ts), no longer `look`, beside `cargo xtask looks` (places, D356) and tools/sandbox/look.ts (a picture's numbers).

## Why

`xtask/src/main.rs`'s single task table was touched by 94 commits since 2026-10-10, every new task and wording change landing on the same lines, so agents working at once on unrelated tools rebased onto each other's edits there. The industry's answer for a registry many hands add to is registration where the thing is defined (Cargo's subcommands found by name, clap's subcommands declared by each module) with one ordered list of the modules; xtask has no build step to collect them, so the list stays, one line a module rather than one block a task. The rename is the building tooling review's finding 3 (research/building-tooling-review-2026-10-16.md): three tools named look, the material bench's the one a new agent took for the places check.
