# D259: Clearing away worktrees

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

`cargo xtask worktrees` lists every worktree and its planned cleanup. On session or subagent start, the hook runs `--prune` in the background at most once every 15 minutes. An idle worktree keeps its build for one hour. Source worktrees still wait two days: only a subagent's under `.claude/worktrees/agent-…`, with all commits on `main`, no changes or untracked files, and no lock is removed with its branch. Idle includes source edits, Git activity and every build file. A process running from or sitting in the build, a Cargo build lock, unreadable Git state, or unavailable process inspection prevents automatic cleanup. A worktree a session still has open (its process sits in the worktree, not the build) keeps its build a day, then has it deleted and seeded again at once. `--done` still deletes a completed agent's build at once. Only worktrees under `.claude/worktrees/` are removed or have their builds deleted.

Every build folder is swept too, since Cargo deletes nothing (`xtask/src/sweep.rs`): in each, the main checkout's, the nightly's and continuous's included, rustc's incremental cache of a unit not compiled for a day is deleted, under the folder's Cargo locks. The shared seed (D183) sweeps itself whenever it is built: every incremental cache, which no worktree is seeded with, and every unit none of its builds names in Cargo's JSON messages, so it holds one build of origin/main. The nightly's and continuous's worktrees, which live long, are seeded again (`cargo xtask seed --renew`) whenever the seed moved on, linking main's new dependencies rather than building them beside the old.

A finished session or subagent is cleaned up at once, not left for the prune: its worktree is removed (`cargo xtask worktrees --done`, or `git worktree remove` by the coordinator when a subagent reports) as soon as its commits are on main.

## Why

The developers, 2026-10-26, after 117 worktrees filled the disk to 90% (94 finished ones removed freed 107 GB): "we should always clean up a completed session immediately too - put that in AGENTS.md".


On 2026-10-15, the developers said "the 2 days is obviously too long" after worktree builds used over 580 GiB. The agent separated disposable build files from source retention and chose one idle hour for builds. Source worktrees retain two days so a lead can resume its agents later. Process inspection protects a live session even between builds; `lsof` is required, and failure keeps the worktree.

On 2026-10-26 the developers: "we have a huge asset cache/etc thats several hundred gb ... make sure our cleanup routines/etc are correct so we dont run out of disk space". The disk held 740 GB; terra 498 GB of it, the seed 282 GB: 178 GB incremental caches no worktree reads and 85 GB of units older `Cargo.lock`s had built, since it was exempt from every cleanup. Every open session's worktree read as in use, so a session left open kept its build for good (one held 35 GB, 26 GB of it incremental). The nightly's and continuous's builds, never seeded again, had grown to 45 and 26 GB. Deleting units by Cargo's own account of what a build uses is exact; `cargo-sweep`'s file times are not, and Cargo's `-Zgc` does not yet reach build folders.
