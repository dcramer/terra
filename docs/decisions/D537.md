# D537: Bevy's per-material change checks run on one thread

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

`check_entities_needing_specialization` and `mark_meshes_as_changed_if_their_materials_changed`, which Bevy runs once for each material type in the game's PostUpdate, gather their entities with `iter` where Bevy 0.20 fans them out with `par_iter`. The work for each entity is a change check and a push. With 26 material types, each fanned-out run waited 0.1 to 0.4 ms on the shared workers, whatever it found; the sky's run, with one entity, took 0.11 ms. The change is a patch of `bevy_pbr` 0.20.0 (`patches/bevy_pbr`, `patches/README.md`), as D184 allows: the systems are Bevy's own, added by `MaterialPlugin`, and nothing of ours can replace them. The entities gathered are the same, only their order differs (the parallel order was never fixed), so nothing drawn changes.

Upstream: Bevy's main still uses `par_iter` (2026-10-27). Drop the patch once a release gathers these on one thread, or once one system serves every material.

## Why

A trace of `world` (`--features trace`, tools/sandbox/spans.ts) had PostUpdate at 5.2 of the game's 9.4 ms, and these two systems at 2.9 ms of it a frame, summed over the material types. `cargo xtask bench world castle town300 going-up` on the Radeon 8060S (RADV), three runs each, at 77d79a67, frame medians and then the game's own work, without the patch and then with it: `world` 8.00 to 7.59 ms (game 7.05 to 6.5), `castle` 5.04 to 4.75 (4.14 to 3.76), `town300` 5.66 to 5.42 (4.84 to 4.5), `going-up` 4.45 to 4.16 (3.7 to 3.4). That is 4 to 7%, where the runs' spread was 1 to 4%.
