# D576: Every build logs what ran long in a freeze; a session's report is written by the game

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Leaning

A frame recorder in `terra_world`, a `tracing` layer over Bevy's per-system spans (Bevy's `trace` feature in every build) and our own spans round heavy work, keeps each frame's spans in fixed buffers a thread. Every frame of 100 ms or more (a freeze) gets one log line naming its world, its five longest systems or spans and the time outside any system; the minute's hitch warning names the system longest in most hitches; the `Loaded in` line names the load's longest steps. With `--profile-report <file>` (the planned `profile` task, the launcher's `Profiling: report`) it also writes, when the game exits, a report of about a hundred lines (the load, the frame by schedule, the slowest frames' systems, the systems by 99th percentile), replacing the Chrome trace and `tools/sandbox/spans.ts`, which are deleted once the report agrees with them. After Unreal's hitch log (`stat DumpHitches`) and CSV Profiler with PerfReportTool. Leaning until its cost is measured: at most 1% of the median frame on `world` and `town300`, else system spans are off unless a report is asked for and the log names schedules only. [launcher.md](../launcher.md#the-hitch-log-in-every-build-d576).

## Why

Perf round 1 (2026-10-29) needed a trace build, a hand launch of the Windows build and a 17 GB Chrome trace grepped down before spans.ts could read it, to learn the first frame spent 5.1 s on mipmaps; and the developer's 1 to 3 s freezes in play never showed in the traced release run, so what froze has to be caught in the session that froze, in the build that was played. A report computed while the game runs writes no trace at all.
