# D431: A push warns when it silently undoes another's recent commit

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

Work lands by `git pull --rebase origin main` onto one's own commits, never by copying files over a fresh main. Before every push, `.githooks/pre-push` runs `node tools/git/undone.ts` over `origin/main..HEAD`, under a second: for each commit and each file it changes that its message doesn't name, a commit of the last 48 hours outside the push is undone there when the push deletes every line that commit added (at least three) and puts back a line it replaced, or it only added. Lines written again elsewhere (a move) and `spike/` don't count; naming the file or the commit's hash in the message says it was meant. It warns with a line an undo and never fails the push, as D37 keeps the hooks to formatting and lints.

## Why

b743f619 (settlement r22, 2026-10-20) wrote stale copies of seven shared files over main and silently undid five commits of the fire and weather agents (453a6321, 52c14076, addbc1ef, 233ca14d, 6fc4ee96) while its message spoke only of the dusk film's camera and light; nothing noticed for hours. The plain rule "a commit deleting another's lines from the last 48 hours on a file its message doesn't name" warned on 94 of main's last 200 commits, since tuning rounds edit each other's lines all day. Requiring an undo (every line gone, and what it replaced back) warns on 11 of the last 400, b743f619 on all seven files among them; the other ten are mostly a workstream rewriting its own generated camera keys. Too few to ignore, too many to block a push on, so it warns, and the rule is written in docs/development.md where landing is.
