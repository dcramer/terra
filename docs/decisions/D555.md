# D555: A render failure fails a scripted run

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

Every run of the sandbox and the game says each render failure once, as a `✗ render:` line in its log on one line (D388): a pipeline the pipeline cache gave up on (its shader did not compile, or wgpu refused the module), named by its label and its shader files, and each error wgpu reports (validation, internal, out of memory, a lost device). A shader not yet loaded is retried by Bevy, so it is no failure. A run a script makes (`--shot`, `--shots`, `--bench`, `--sheet`, `--background`, `--remote`) goes on past a validation or internal error, so its pictures are made and every failure is listed, and then exits 1 however it ended, with `SANDBOX ✗ N render failures, so the run fails:` and the lines; a lost device or memory ends it at once. A person's play quits on a wgpu error, as Bevy's own handler does. The remote's `status` and `shot` name the failures, and `shot`, and every script shooting through `tools/sandbox/client.ts`, exits 1 on one. It is `crates/terra_world/src/render_errors.rs`: the pipeline cache read as the render world extracts, while pipelines are being made, and our `RenderErrorHandler` in place of Bevy's. D549's test catches what does not compile before a run; this catches what the test cannot model and what wgpu refuses at run time.

## Why

A shader that does not compile draws nothing, and the only sign was a line in the log while scripted runs and films went on and passed (the sky lost its clouds that way, D549). Bevy's own handler quits on any wgpu error, which ends a run without saying what had already failed and leaves pipeline failures silent. A failing run is what a script and an agent notice; a line in a log is not.
