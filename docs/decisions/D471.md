# D471: Asset sets by theme, a record per instance, replication by instance

Area: Engine and code · Owner: Tech · By: Agent · Status: Leaning

How an instance's files, saves and messages are bounded ([instances.md](../instances.md#asset-sets-d471)):

- **Asset sets.** A theme names its set in its data (`assets/data/sets/<theme>.ron`); entering loads it as a world resource of strong handles, tracked by `Progress`; leaving drops it. Bevy's handles are the reference count, so an asset another holder still uses stays and the rest is freed, on the GPU too. The new set is taken before the old is dropped.
- **Records.** The character's record (body, vitals, skills, items, return stack, where they are) is apart from each instance's: its spec, its operations in the server's order (D21) and a section per module with state beyond its rules (`app.save_section::<R>()`), in RON through serde (D353). Leaving a world writes its record; returning reads it: frozen is saved. `play::save` splits into the two.
- **Replication.** A connection is subscribed to one instance at a time, and within it by area; world messages carry the instance's epoch and the client drops those of one it has left. The character and the session travel on the player's own channel.

## Why

Reference-counted handles are how Bevy already frees what nobody holds; taking the new set first keeps what two worlds share from being freed and loaded again. A world is computed, not stored (D47), so its record is operations and module sections, not Bevy's `DynamicWorld`, which would store chunk meshes and every derived component. Splitting the character from the world is what lets a character cross between worlds and servers (Minecraft rebuilds an entity in the other dimension from its saved data; Unreal carries the player state). An epoch keeps a late message for the old world from landing in the new one.
