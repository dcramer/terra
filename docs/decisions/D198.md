# D198: The game in layers

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

`terra_game` is three plugin layers, each standing only on those before it: the world (data, light, the day, what grows, the tick, levels of detail, on the planet, terrain and the start), the walker (a body this machine steers, its camera, controls and options), and gameplay (everything a player does). They are bundled as `GamePlugins`; the full game turns on all three, and a run can leave layers out, as the sandbox's `walk` does. A layer never needs a system or resource above it to run: it orders by system sets, publishes small types the layer above fills in (`Hands`, `ArriveAt`, `WarpTo`), adds what it owns to new entities with observers, and takes what may be missing as optional. The start is the world's, chosen from the planet, not the build's. The world is its own crate, `terra_world`, under `terra_game`, which holds the walker and gameplay; the world owns the types the game meets it through (`Footprint`, `Viewpoint`, flora's items by name). See [tech.md](../tech.md#layers-of-the-game-d198).

## Why

The developers on 2026-10-13: "we want modules pluggable and mostly large enough chunks i.e. not 'microservices' equivalent. And we want main game to still do pretty much entire thing, but we are doing it so its better to test and build modules in isolation", and "lets make sure this also is like a proper bevy/ecs pattern". Walking through the forest needed all fifty of the game's plugins, since the build held the start and every screen was read by name. Plugin groups, system sets, observers and run conditions are Bevy's own ways to compose plugins. Checked by tracing the game before and after through the same keys: the player's state agreed on every frame; only creatures at reduced detail think on other ticks, since entities were spawned in another order.
