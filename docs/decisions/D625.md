# D625: Character work starts from one status command over recorded results

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

What character work must hold and what is next is data, `tools/characters/criteria.json`: the checks whose results are recorded (the wardrobe check, `wardrobe.ts`, and the body build, `build_bodies.sh`), each with the command that refreshes it, how long it takes and the files it reads; a row a criterion (a stage of a check, the build's verdict with its known faults and why each is allowed, or a reading of the catalogue made as the status runs: the looks' hair, the dressed figures a body against D182); and the tasks still to do, in order, each with the files that own it (`path#symbol`, resolved to the symbol's line as it prints) and the command that checks it. `cargo xtask characters` (`tools/characters/status.ts`) prints it in 40 lines or fewer: each criterion ✓, ✗ or ? (stale or never measured) with its number and, when not passing, its bar; each check's last record, how stale it is and the command that refreshes it; the tasks, those whose criterion fails first; and the next thing to run. It runs no check, so it takes a second.

A check records what it said, a line a stage, when it runs (`tools/characters/record.ts`), with the commit and the files uncommitted then, in `~/.cache/terra-characters/<check>.jsonl`, per machine, so a fresh job's worktree sees the last results. A record is stale when a commit since it touched a file its check reads, when it ran on uncommitted changes to one, when one is changed in the worktree reading it, or when it ran at a commit the worktree does not hold. It is the first thing the character skill tells a job to run, as combat's scorecard (D452) and the controller's (D457) are; a job that finishes a task takes its row out of `criteria.json`, and one that finds work adds a row, so the handoff no longer has to carry where things stand.

## Why

The developer, 2026-11-05: "the efficiency is CRITICAL here so we can design characters that are great. people online have figured this out with agents, you must too". The last six character jobs spent 111k tokens of context before their first edit, rebuilding where things stand from the log, the handoff, decisions and code (research/2026-11-05-agent-pipeline-tokens.md, measured by `tools/token-stats/job.mjs`); combat and the controller start from a scorecard command instead. Their checks are cheap; the character checks are not (the wardrobe check 80 s on every core, the build minutes of Blender), so the status reads what they last said and says how stale it is rather than running them. There is no ratchet yet: the criteria are stages that pass or fail, and none has a number a change could worsen by degrees; one comes when a criterion does (the worst poke of a pairing, the rig's worst joint).
