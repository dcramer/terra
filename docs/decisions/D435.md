# D435: Vertex buffers packed in ordinary memory before the upload

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

A mesh's vertex buffer is packed in ordinary memory, a run of 64 KiB of vertices at a time, and each run copied into the GPU's staging memory in one sequential write. Bevy 0.20 interleaved it attribute by attribute, a 4-16 byte write for each attribute of each vertex, straight into the mapped staging slice the mesh allocator hands `Mesh::write_packed_vertex_buffer_data`. That memory is write-combined, so scattered small writes into it are slow. The change is a patch of `bevy_mesh` 0.20.0 (`patches/bevy_mesh`, `patches/README.md`), as D184 allows, because the packing is inside `Mesh` and the allocator, with nothing of ours beside them to extend. A test (`terra_world`'s `mesh_upload_tests`) holds the packed bytes to the offsets of Bevy's vertex buffer layout for a mesh of eight attributes spanning several runs.

Upstream: no fix on Bevy's main (2026-10-22, the function unchanged); the nearest issue is [bevyengine/bevy#17000](https://github.com/bevyengine/bevy/issues/17000), `Mesh` interface works against performance, which measures `write_packed_vertex_buffer_data` at 40% of `allocate_and_free_meshes`. Drop the patch once a release packs off the mapped memory.

## Why

Castle fall round 16 traced every 250-820 ms render-world hitch to `allocate_and_free_meshes`, about 15-18 ms a MiB of vertex data, ~60 MB/s, 2.3 s for the castle's first 190 MiB (~/.cache/terra-review/final/castle-fall/r16/allocprobe.txt). The same upload serves terrain streaming everywhere.

After, `cargo xtask gpu bench -- node tools/sandbox/qa.ts castle --part tower` on the RTX 3080, main bd8f72cc against it with the patch, each with a throwaway probe timing the allocator (castle-fall/r17): the allocator 16.5 to 1.2 ms a MiB of vertex data (1,583 MiB over 302 frames in 26.1 s, against 1,568 MiB over 357 frames in 1.9 s); the castle's first 190 MiB 1,946 to 118 ms; the run's 99th percentile 167.7 to 26.7 ms, its hitches 144 to 26; the tower stage's median 15.5 to 14.4 ms. In a `trace_chrome` build, `allocate_and_free_meshes` took 13.4 s of the run, 92 times over 30 ms, and now 1.1 s, 3 times. The bytes uploaded are the same, so nothing drawn changes.
