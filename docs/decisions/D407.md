# D407: How the crates are cut

Area: Engine and code · Owner: Tech · By: — · Status: Open

Recommended ([research](../../research/2026-10-18-crate-layout.md)): cut `terra_build` (71k lines) and `terra_game` (60k) into domain crates of some 6 to 17k lines. Building's plain Rust becomes the rules, the layout (where pieces go, which a server needs) and the drawing (which it does not), and settlements become `terra_town` with `terra_life` merged in. The game becomes the base on screen, the walker, survival, and above it creatures, townsfolk and building play side by side, under a thin `terra_game`. The world stops depending on building (`Walker` into `terra_core`, the start fitted to a plot of its own). Cargo then holds D198's layer rule, since a crate cannot name one above it, and D28's list of crates on Bevy grows to nine. It lands in small pushes, each measured with `cargo build --timings` against a baseline. Open: whether this is the granularity the developers meant by "large enough chunks" (D198), whether `terra_life` merges, and the names.

## Why

The developers asked for obvious speedups and named "segmenting the game modules so they look like a larger-scale Rust/Bevy game" as part of it (2026-10-18). On D198 they asked for modules "pluggable and mostly large enough chunks i.e. not 'microservices'", so this is theirs to agree before anything moves (D49). A touch-only dev rebuild of the sandbox pays `terra_build` 29 s, `terra_world` 23 s and `terra_game` 16 s in series, and release builds, which every shot, film and bench runs, are not incremental. Veloren's server compiles without its graphical client, and matklad's measure is what a crate does not depend on.
