# D409: Rendered indexes merge row by row

Area: Tools and workflow · Owner: Tech · By: Agent · Status: Decided

An index of files that live on their own is rendered from them and never edited by hand: `docs/decisions.md` from `docs/decisions/` (D389) and `research/README.md`'s table from the notes, each note's title and the date at its top, newest first (`node tools/docs/docs.ts --render`). Both stay committed, so they read on GitHub, and git merges them with a driver of ours (`tools/docs/merge.ts`, `merge=rendered` in `.gitattributes`, which any `cargo xtask` task sets up for a clone and `cargo xtask doctor` checks): each side's index is a function of its files, so it merges row by row, keyed by what a row links to, each side's added, changed and removed rows kept and put back in the page's order. Two agents adding a decision or a note at once never conflict and never leave a stale or misplaced row. What it cannot place (one row changed two ways, the page round the index changed on both sides) is an ordinary conflict, which `--render` mends.

## Why

From the 2026-10-18 review of rework: `docs/decisions.md` was touched by 17 commits since D389 under `merge=union`, which keeps both sides of a changed row, so a status changed beside another agent's new row left a stale copy and a red docs check; `research/README.md`, hand-kept, by 84, its rows appended at the end until some landed below its "Adding a note" section. Generating each in the commit alone still has every commit touching the same lines; the industry's answer for a generated file is a merge driver that rebuilds it (npm's lockfile driver) or fragments rendered at release (towncrier). The files are already fragments, so the driver is enough, and keeps the indexes committed and current.
