# D361: Bevy's glTF loader behind a gate, its IO pool Bevy's own

Area: Engine and code · Owner: Tech · By: Agent · Status: Decided

Under D184, Bevy's `GltfPlugin` is replaced by `terra_world::gltf_gate::GatedGltfPlugin`, which registers Bevy's own loader, unchanged, behind a gate letting as many loads through at once as the IO pool has threads; it takes `GltfPlugin`'s settings, so a glTF setting (a custom vertex attribute) goes to it. The IO pool is Bevy's default again, its threads 2 MiB of stack, not the 32 MiB set to make room for the nesting.

## Why

Bevy 0.20's loader decodes a model's images in a scope on the IO pool, and a thread waiting in a scope runs other glTF loads queued meanwhile inside it, a load deeper on its stack for every model loading at once (bevyengine/bevy#15271, open): the yard's startup on Windows went 84 deep, 2 MiB of stack, and died of an IO thread's stack overflow every time on 2 MiB threads (the frames check's intermittent startup crash). With the gate a waiting load yields instead of nesting, so a thread holds at most four, 72 KiB, however many models load, and loading took no longer (`tests/gltf_gate.rs` loads every model at once on 256 KiB stacks; without the gate it overflows every time). A bigger stack only moved the limit, which a town's hundreds of models would reach.
