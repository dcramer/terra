# D398: The gates scale with the change

Area: Tools and workflow · Owner: Tech · By: Developers · Status: Decided

The check before a commit is linters and at most fast unit tests, budgeted at a few tens of seconds on a built tree (30 s, `COMMIT_BUDGET_SECS`; it says when it is over); every big suite runs in the full check, which CI runs on every push to main (D37). Each gate runs only the stages that can see what the change touches (`xtask/src/scope.rs`), and `--all` runs a gate over everything.

**What a change is.** Before a commit, the tracked files that differ from HEAD; before a push, everything that differs from the merge-base of HEAD with origin/main. A file in a crate's folder is that crate (xtask's for the tasks); `assets/` is read by the crates on Bevy, and its building, life and climate data by the crates reading them too (D406); the files outside the crates that a crate reads, those under `assets/` among them, are listed in `READ_BY` (the demos' `places.ts`, the voxel contract's JSON, `art/`), and a test fails when a crate names a repository path outside its folder that is not listed. `tools/<dir>`, the docs, the agents' folders, the hooks and the top-level notes are seen by their own checks. A change to the workspace's manifest, its lock, the compiler or cargo's or clippy's settings, or a file the rules cannot place, runs everything.

**Before a commit** (`cargo xtask check --quick`): formatting when Rust changed, the size and one-definition gates, the docs check and the shared crates' repeatability always; clippy and the tests (`--tests`: no examples' builds, no doc tests) of the changed crates only, without `SLOW_TESTS`; the tests of the tools changed; the Bevy rule when a manifest changed.

**Before a push** (`cargo xtask check`, since 2026-10-18, D37): what runs before a commit, over everything since the merge-base, with the crates reading a changed file.

**The full check** (`cargo xtask check --full`; `--all` over everything, as CI runs it on every push to main): clippy and every test, the slow ones too, of the changed crates, the crates reading a changed file, and every crate depending on any of them (cargo's own inverted tree, dev dependencies included), with xtask, whose tests read every Rust source, whenever Rust changed; all the tools' tests; the kit checker and the artifacts and fuzz ratchets when building or a crate under it, the assets or the tasks changed; the foliage check when the assets or the textures tool changed; the Blender scripts' check when a Python script or the Blender tool changed.

**What is no longer run, and why that is safe.** A commit no longer lints or tests the crates depending on the one changed, runs no slow test, kit, foliage or other tool's check: the full check runs them on main once the change lands, and names the commit that broke one (D37). A push no longer tests a crate that neither changed nor depends on what changed: its code and everything it reads are as on origin/main, which passed the same gate when it was pushed. The rule is conservative where it cannot tell: anything unplaced runs everything.

`SLOW_TESTS` holds every test over five seconds on the loaded machine (45, from 4), each marked on its `#[test]` line: the drawing sweeps, the town and village laid whole and lived through a day, the land's place finders, the mountains sampled finely.

## Measured

On the 24-core machine with four other agents building and rendering (load average 30 to 135), on a built tree:

| | Before | After |
|---|---|---|
| A commit of docs and settings only | 3m 12s (the whole quick check) | 0.8 s (sizes, one definition, docs) |
| A commit changing a leaf crate (terra_items) | 3m 12s | 13.2 s |
| A commit changing terra_build | 3m 12s | 10.1 s; 1m 25s on the first run after an edit, compiling its test binary |
| A push of a docs or tools change | 24m 21s (the full check: another agent's push, run alongside) | 2.1 s |
| A push changing terra_items (terra_game and terra_sandbox tested with it) | 24m 21s | 51.6 s |
| A push changing building, the land and the tasks (this change's) | 24m 21s | 24m 35s: the slow sweeps still run, and are most of it |

The quick check's tests were 2m 52s of the 3m 12s, all of it running tests, none compiling: the test binaries run one after another, terra_build's for 142 s and terra_land's for 72 s, each bound by its few slowest tests. A worktree behind what it last built adds the compile on top, about 4 minutes for every workspace crate under this load: the evidence's 9-minute tests stage. cargo-nextest would run the binaries side by side, but a building push is bound by single sweeps of many minutes each, so it is not worth a dependency; making those sweeps quicker, or moving them to CI, is what would shorten it.

## Why

The developers, 2026-10-17: "i think there were fixes to making pre commit checks faster. they are too expensive now", and "theres a difference between big suites of tests performance tests rendering pipelines etc. vs like linters and at most units. precommit checks shouldnt take more than like a few to few tens of seconds, rest should be bigger checks. we can later on run on ci". A commit touching only `.claude/settings.json`, two docs and a README had run the whole quick check in 11 minutes, and pushes 18 to 40; agents waiting on the hooks were a large share of what the token audit found spent.
