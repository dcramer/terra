# D37: Repository tooling

Area: Tools and workflow · Owner: Tech · By: Developers · Status: Decided

One Cargo workspace at the root with a pinned compiler. Git runs two hooks from `.githooks`, switched on by any `cargo xtask` task, and `--no-verify` is not used. They format and lint, and nothing else: before a commit `cargo fmt --all --check`; before a push `cargo xtask check`, formatting and clippy of the crates changed since the merge-base with origin/main (the workspace when the build itself changed, D398), in seconds. No test, ratchet or other crate's build runs in a hook; an agent runs the tests of what it changed itself. Landing is plain git: `git pull --rebase origin main`, then `git push origin HEAD:main`, again if main moved.

The full check, `cargo xtask check --all` (formatting, the code-health gates, clippy and every test of the workspace, the slow ones too, every tool's tests, the kit, foliage, artifacts and fuzz checks, the docs check, the Blender scripts where there is a Blender, and the shared crates' rules), runs in GitHub Actions only when started by hand (`.github/workflows/main.yml`, `gh workflow run main.yml`), on Linux with no GPU; there is no CI on a schedule or on a push while we are pre-release. When it fails it opens, or comments on, the issue "main fails the full check", with every stage's log kept as the run's artifact `check-logs`; the next passing run closes it. There is no check on each push, no bisect and no automatic revert: whoever's commit broke it fixes it before more lands on what it touches.

`cargo xtask nightly` (D411) stays as it is, run continuously on one machine of ours by the CI agent (`cargo xtask ci --watch`, [ci-agent.md](../ci-agent.md)): it runs the artifacts ratchet over every scene, bisects its own failures, and is the one place a baseline is lowered (D414). The heavy checks that need a GPU or run for minutes (GPU renders, the fire sheet, look checks, benches) are continuous checks on main, `cargo xtask continuous` ([tools/continuous](../../tools/continuous/README.md)) on the GPU machine, each a row of `checks.json`, reporting a regression with the commit range it came in (`.git/terra-continuous/status.txt`). `ci.yml` runs the full check on Linux, macOS and Windows, and a compile check for the Windows target we cross-compile from WSL, only when started by hand. `cargo xtask doctor` checks a machine, and `cargo xtask win` runs a Windows build on the GPU from WSL. `AGENTS.md` holds the instructions for every coding agent; `CLAUDE.md` only points to it. Agent skills live in `.agents/skills`, with `.claude/skills` linking to it, so every coding agent finds them.

## Why

Two developers on different platforms, and agents writing the code, need one command that says whether a change is acceptable. Tasks are written in Rust so they run the same everywhere. CI turned off on 2026-10-12: "im not sure CI is really adding much value rn btw, worth disabling it til we need it".

Re-scoped on 2026-10-19 by the developers: "Yes: re-scope to this model. Pre-push gate of 2-3 min (fmt, clippy on changed crates, cargo check of every dependent crate, unit tests of changed crates without slow sweeps); nothing heavy before commits; plain git pull --rebase && git push; full check scheduled a few times a day in GitHub Actions opening an issue when red; no per-push CI, bisect or auto-revert for now; remove land, slots, stamp and tiers; subagents count in the agent limit. Update D37 and supersede D413." And: "we're early in dev cycle so its not critical. we also dont want pushes taking forever, but we'd ofc like to avoid pushing broken builds." Then, cutting the push's gate further: "like why do we have a heavy pre-push gate. just have linters and formatters run per normal you're going fucking crazy", and "it really doesnt need to be 2-3m thats slow af". They had called the process before it "an awful wacky dx": a commit's check of linters and the changed crates' tests, a push's of most of an hour under load, a turn to land with stamps and machine-wide check slots (D413), and a run on every push to main with a bisect. A fault the hooks miss reaches main and is found by whoever runs the tests of what they change. Then, on 2026-10-19, of scheduling it: "we're pre-release so we dont need CI really yet", so the 8-hourly run was turned off and the workflow kept for running by hand.

Measured on 2026-10-19 on a built tree, a one-line comment appended to a terra_build source: before, the commit's hook took 4m 13s (clippy 1m 00s and tests 3m 06s, compiling after the edit, load 115) and the push's 36.9 s after it (its tests 29.7 s, load 25); after, the commit's 4 s and the push's formatting and clippy 5 s at load 13, and through the hooks at load 88 the commit's 25 s and the push's 45.3 s (fmt 9.7 s, clippy 35.3 s): load, not the gate, sets it now.

Continuous checks on main added on 2026-10-18, after an agent had made the fire sheet a step before landing every change to fire: "why did you decide that every commit must do a fire check? this should be a check for continuous main checks, not for precommit hook, that would be too expensive. if there is some guidance that suggests that, it should be reworked and mention that precommit hooks are mainly for simple quick tests/formatting/linters and etc. and that tests like these are to be ran on main via continuous tests".
