# D556: An error says what to do

Area: Tools and workflow · Owner: Tech · By: Developers · Status: Decided

Every error our code, tools, checks and gates give is written for the agent who will read it next, and steers it the way we intend, never a bare complaint. It says, in a few lines:

- **what** went wrong, with the thing named (the file and line, the entity, the tunable, the shader, the seed);
- **why it is wrong here**: the rule it breaks, with its decision (`D396: a function over 150 lines`), so the fix keeps the rule rather than working round it;
- **what to do**: the fix we want, or the command to run next (`split it; cargo xtask sizes`), and what not to do where the tempting fix is wrong (`don't raise the baseline: only cargo xtask nightly lowers one, D414`);
- **where the rest is**: the log or file with the details (D388).

As rustc's `help:` and `note:` lines and Elm's compiler messages do. A panic message, a test's assert, a check's fault, a refusal over the remote and a tool's exit all count. A message that only says what failed is a fault to fix when it is next met.

## Why

The developers, 2026-10-27: "another guiding principle: errors should have agent-debuggable messages to go with them, that steers them towards the intended direction we would desire, vs just a freeform error".

An agent reads an error with nothing else in front of it, and picks the nearest fix it can see: a freeform error invites one that works round the rule (raising a baseline, skipping a check, guessing a value) instead of the one intended. Naming the rule and the wanted fix costs a line where the error is written, and saves a turn, or a wrong commit, each time it is read. D388 keeps the output short; this says what the short output must contain.
