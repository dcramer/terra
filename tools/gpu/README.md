# tools/gpu

The GPU wrapper (D319): every unattended GPU run an agent starts goes through it. Shots, sheets, films and bakes start at once; only a benchmark has the card alone. There is no queue for the card and no memory admission; a run that starts the game waits only for the game's one copy.

**One game copy a machine** (D319): the game refuses to start while another copy of it runs, Windows and WSL counted as one (`terra_world::single_instance`), so under the wrapper a command that starts the game waits for that one copy instead of starting and being refused (`turn` in `gpu.ts`):

- **Which commands**: every command is taken to start the game, as nearly all do, most through a script or task that names no game; but not a Blender run (`blender`, `tools/characters/`), a `--multirun` copy, or one given `--no-game` (`isGame` in `plan.ts`), which start at once. Pass `--no-game` for any other long run that starts no game, so it holds up no game run.
- **The queue**: first come first served among the wrapper's game runs, by when each joined (its run file's `queued`, the lower pid on a tie); the one whose turn it is holds `gpu.game/<folder's hash>.lock` beside `gpu.lock` for its command's whole life, in a helper (`flock … cat` on a pipe from the wrapper) so the kernel frees it however the wrapper ends and the command never inherits it. A script that runs several copies one after another (the duel's four) keeps the turn throughout.
- **A copy started outside the wrapper** (someone playing, a run by hand, an older checkout's wrapper): the run with the turn then waits while either slot's record (`instance-<n>.txt` in the game's instance folder, `TERRA_INSTANCE_DIR`, under WSL the Windows `%LOCALAPPDATA%\terra`) beats, as the game itself tells a live copy across the WSL line; a dead copy's record, unchanged for 3 s, holds nothing up. Should such a copy take the machine while the run builds, the game refuses it and the wrapper waits and starts it again, up to three times.
- **What it says while it waits**: at first and every 2 minutes (under the 5 minutes of silence a background run is ended at), `gpu: film waits for the game's one copy a machine (D319), held by …`, naming the wrapper run (class, pid, worktree, command, how long it has run) or the outside copy (pid, system, worktree, command). `--status` shows the same on the waiting run's line. Waiting is not a stall. A wait that would pass an hour is not a wait: hand off (D400).
- A bench waits in the same queue before it waits for the card; a render slot, with an instance folder of its own, has a queue of its own. Without `flock` there is no queue and the game refuses as before.

Only a two-player test on one machine passes `--multirun`, which allows exactly one more copy; nothing allows a third. The render box keeps its three slots (tools/render-worker gives each its own instance folder).

```bash
cargo xtask gpu still -- target/release/terra_sandbox --offscreen ... --shot a.png > run.log 2>&1
cargo xtask gpu film --watch out/render.log -- node tools/sandbox/trailer.ts --cut ... > film.log 2>&1
cargo xtask gpu bench -- cargo xtask bench walk
cargo xtask gpu --status
```

Start it with Bash's `run_in_background` and wait for its completion notice.

- **Classes**: `still` (a few stills or vantages), `sheet` (a sheet at a small place: the yard, the fire sheet, a workbench), `film` (a film or a long probe at a big place), `bake` (a bake-off or sweep over several scenes), `bench` (a benchmark). Only `bench` is treated apart; the rest differ by their stall limit (`CLASSES` in `plan.ts`).
- **Shared runs** (`still`, `sheet`, `film`, `bake`) run the command at once under `flock -s ~/.cache/terra/gpu.lock` (`TERRA_GPU_LOCK`), held for the run's life. They wait only while a benchmark wants the card.
- **Benchmarks** leave a want-file, `gpu.want/<pid>` beside the lock, then run under `flock -x`: they wait for the shared runs holding the lock to end, run, and remove the want-file. While one is there, new shared runs hold back, so a bench is never starved. A process waiting for the lock alone by other means (the game's own bench, `flock -x` by hand) holds them back too. The game finds the turn held by a forebear and waits for neither the lock nor a slot (`terra_world::gpu_turn`).
- **Stalls**: a run is stopped (TERM, then KILL after 10 s) and exits 124, with the reason printed, only when, holding the lock, its whole process tree has made no progress for its class's stall limit: 5 min for a still, 8 for a sheet and 10 for the rest. Waiting for the lock is not a stall. Progress is any of: output on its stdout or stderr, growth of a `--watch FILE`, its CPU time growing (utime and stime from `/proc/<pid>/stat`, reaped children's included, or `ps -A -S` where there is no /proc, as on macOS, summed over its processes, at least 5% of a core over a minute), or one of its processes busy on the card's cores (`nvidia-smi pmon`). So a silent run that renders or computes is left alone, and a hung one, which uses nothing, is stopped at the limit. Under WSL a Windows program's CPU and GPU use are not seen from Linux, so it is judged by its output and `--watch` alone. `--stall MIN` changes the limit. `--vram MB`, the old scheduler's memory request, is accepted and ignored.
- **What it says**, on stderr with a `gpu:` prefix: a line if it waits for a benchmark (and every 5 minutes after), a line when it starts after waiting, a line when it ends, which for a start the game refused (another copy runs) says so and what to do (`refused` in `plan.ts`). It exits with the command's code.
- **`--status`**, for the coordinator: the card's memory, each run (running or waiting, its age, time since its last progress, pid, worktree, command), whether a benchmark wants the card, and whoever else holds or waits for `gpu.lock` (`outside`).
- **A holder no run owns**: a process a run started in the background (a `setsid` loop) inherits the lock's open file and holds the lock after its run ends, while /proc/locks names only the long-dead `flock` that took it. So the holders are read from who has the file open (`/proc/<pid>/fd` and `fdinfo`), and one that is no live run's, nor started by one (its `TERRA_GPU_JOB`), is shown in `--status` with its age, folder and command; past 3 minutes (`OUTSIDE_MS` in `plan.ts`), `--status` and every 5 minutes a run waiting on the lock name it (pid, command, folder, the ended run and render job it came from) and how to stop it (`kill -- -<pgid>`), or to wait for a run started by hand. A cancelled render job's clippy loop held slot 4's lock 2 h 46 min this way on 2026-10-29.
- **State**: a file a run in `~/.cache/terra/gpu/runs/` (`TERRA_GPU_DIR`), with its wrapper's pid and its command's. A run whose processes are all gone is removed by the next reader, and a want-file whose wrapper died likewise.
- **Nesting**: a job's command runs with `TERRA_GPU_JOB` set. A `cargo xtask gpu` inside it runs its command at once, since it already has the turn.
- **Tests**: `node --test tools/gpu/*.test.ts`. `gpu.test.ts` runs real processes on their own state directory and lock: two stills start at once, a bench waits for a running still and holds back one asked for meanwhile, two game runs asked for together run one after the other while a `--no-game` run starts beside them, a game run waits out a copy beating outside the wrapper and no dead copy's record, a run the game refused once is started again (the stand-ins are `sh` commands, never the game; with the queue switched off those three fail), a silent busy loop survives and a silent sleep is stopped.

`plan.ts` holds the pure parts: the classes, reading nvidia-smi, /proc/locks and /proc stat lines, and the progress rule, tested in `plan.test.ts` without a GPU. `gpu.ts` takes the lock, runs the job and keeps the state. It needs Node 22.18 or later and `flock` (util-linux); without `flock`, as on macOS, it runs the command with no lock and the game takes its own turn (`gpu_turn`); the lock-order test is skipped there. `nvidia-smi` is optional.

`flock ~/.cache/terra/gpu.queue` is a dead path: nothing takes it. Replace it with `cargo xtask gpu <class> --`.
