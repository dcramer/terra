# Sandbox remote

Drives a running sandbox from the command line over Bevy's remote protocol (D69): find things, move them, hold the camera on them, pause and step the clock, press keys, read what is true and what the run has said, wait for something to happen, pose a model, and take screenshots, all without restarting. Use it whenever you would otherwise change a number and restart to see the result, such as placing a socket, fitting gear or framing a shot, and to test a feature in one running game instead of a scripted run per step. TypeScript, run directly by Node 22.18 or later, with no dependencies.

```bash
r() { node tools/sandbox/remote.ts "$@"; }

r start --windows -- --experiment workbench --model models/character/base.glb --hold stone_axe --anim Walk_Loop
r find socket.hand                       # names containing it, with where they are
r pose Walk_Loop 0.6                     # every model held 60% through the walk
r shape --model 0 heavy=0.5 strong=0.3   # the first model's body, half heavy and a little strong
r look socket.hand.R --distance 0.9 --around 90
r place socket.hand.R --rotation 70,0,0  # its local transform; rotation in degrees
r shot shots/hand.png                    # waits for the file
r stop
```

Testing a feature in play, in one running game:

```bash
r start --windows -- --experiment play --fresh --save test.ron
r give bow quiver arrow:4                # waits until each is given
r warp -32,34 --facing -45,36            # waits until the player is there
r state                                  # where they are, their body, what they carry, what is near
r snap before                            # keep it, to say later what changed
r aim -45,36 --up 0.8                    # the middle of the view on the deer's chest
r press 5 e@10:60                        # the bow, then ten frames later draw for 60 and loose
r wait "An arrow hit" --timeout 20       # or fail, showing what was said instead
r said                                   # everything said since the last action
r diff before                            # only what changed since: ~ health: 100 -> 80, - carrying.arrow: 1
r why Player Transform                   # tick.rs:166 in show, …; drawn between ticks, last moved outside the ticks by walker.rs:512 in warp, frame 484
```

Trying values of a number in one running game, with no rebuild ([tunables](../../docs/development.md#tunables), D547):

```bash
r start --windows --release -- --experiment play --quality high --time 15 --vantage-ground --vantage 0,4,0,-600,450,300
r tune list sky.cloud                    # name = value (default, range, who set it): what it does
r pause
r shot shots/cover-0.5.png
r tune set sky.cloud.heaped_cover 0.25   # sky.cloud.heaped_cover: 0.5 -> 0.25 (default 0.5)
r shot shots/cover-0.25.png
r tune reset                             # back to their defaults: sky.cloud.heaped_cover
```

The same tunables on the debug menu's sliders (D81, [development.md](../../docs/development.md#debug-menu)), driven as a person would:

```bash
r start --windows --release -- --experiment play --debug-menu
r press backtick                         # opens it: "Debug menu: open" in the log
r menu --search heaped                   # sky.cloud.heaped_cover = 0.5 (default): slider 212 to 388 at y 273, reset at …
r click 256,273                          # a quarter along: Tune: sky.cloud.heaped_cover 0.5 -> 0.25 (…, by debug menu)
r tune get sky.cloud.heaped_cover        # = 0.25 (default 0.5, 0 to 1, by debug menu)
```

`start` runs the sandbox in the background on a port nothing else answers on, records the port in `shots/remote.port`, and waits until it answers; every other command talks only to that port, so commands never reach a sandbox another session is driving (`TERRA_REMOTE_PORT` overrides it); anything after `--` goes to the sandbox, and `--windows` runs it on the Windows GPU from WSL (`cargo xtask win`), which is much faster than WSL's CPU renderer. Its log is `shots/remote.log`. A sandbox started by hand with `--remote` works the same. `start` also passes `--steady`, so the game moves a sixtieth of a second every frame however fast frames are drawn, as scripted runs do: a key held for 60 frames is a second of play on any machine. `--real-time` leaves the clock alone. It passes `--background` too, so the run stays out of the way of whoever is at the machine: its window opens behind the others without taking focus, never takes the mouse, ignores the real keyboard and mouse, and is silent; only the script drives it. `--foreground` gives a normal window, to play alongside the script.

| Command | What it does |
|---|---|
| `start [--windows] [--real-time] [--foreground] [-- options]` | Start a sandbox listening, and wait for it |
| `stop` | Close it |
| `find NAME` | Entities whose name contains NAME: id, where they are, their local transform |
| `place NAME [--translation x,y,z] [--rotation x,y,z] [--scale s]` | Set the local transform of the entity called exactly NAME |
| `look NAME\|x,y,z [--distance m] [--around degrees] [--height m] [--aim m] [--from x,y,z]`, `look --vantage x,y,z,x,y,z` | Hold the camera on an entity, following it, or a point; `around` is from the model's front, `aim` how far above it to look (a person's position is their feet); `from` puts the eye at a point in the world; `--vantage`, as the sandbox's option and the kit sheet's log give it, an eye and what it looks at from the start |
| `release` | Let the camera go |
| `pause`, `resume` | Stop and start the game's clock, animations included |
| `step FRAMES` | Stop the clock, let it run that many frames, stop it again, and wait until it has |
| `press KEY[@AFTER][:FRAMES] …` | Hold keys, named as `--press` names them, for so many frames (one if not given), starting so many frames from now (none if not given): `e`, `w:60`, `f@40`, `e@90:80`. A sequence of keys goes in one command, timed against the game's frames rather than the script's |
| `status` | The frame, the game's time, whether the clock is stopped, whether the loading screen is up, the next line's number, and the run's render failures (`render_failures`, D555), each also said as a `✗ render:` line after it |
| `call sandbox.frames {"seconds": 10}` | How the frames of the last so many seconds went on the real clock: median, 99th percentile and worst of the time between frames, their work, the game's update and the GPU's, to time a stretch of play |
| `call gpu.memory {"top": 20}` | What fills the GPU's memory, from wgpu's allocator (`crates/terra_world/src/gpu_memory.rs`): this process's blocks now and at the run's peak, by the label each allocation was made with (numbers folded, so every mesh slab sums as one), and the peak's textures by asset and meshes by the named entity that draws them. Every run also logs a line at each new 256 MiB of peak and the whole breakdown as it ends. `(wgpu internal) Staging` is upload memory, host-visible and mostly in system RAM; the rest is on the card |
| `said [--containing TEXT] [--all] [--from LINE]` | What the run has said since the mark, with the frame of each |
| `wait TEXT [--timeout s]` | Wait until the run says something containing TEXT since the mark; on timeout, show what it said instead and fail |
| `mark` | Start `said` and `wait` from now |
| `state` | In play: where the player is and faces, their body, what they hold, carry and wear, and the creatures and people within 40 m |
| `snap NAME` | In play: keep `state` and `build.state` as `shots/snaps/NAME.json` (D400) |
| `diff A [B\|now] [--epsilon m] [--most N]` | What changed from snap A to B, or to the run now: a line a change, `~` changed, `+` appeared, `-` went, `#` how many changed, numbers within 0.01 the same, at most 40 lines and a count of the rest. Things in a list are matched by what they are (`id`, `name`, `who`, `what`, `kind`), and among several of a kind, nearest to nearest by `at` ([snap.ts](snap.ts)) |
| `why ENTITY [COMPONENT] [--json]` | What changed this? (D548): who spawned an entity, given by the id `find` gives or by name (exactly, in any case, then a part of it, as `find`), and for each of its components, or those named (by type path, as Bevy's `world.*` methods name them, by name in any case, then a part of it), the line of code and the function it is in (for a system, its name) that last changed it, and on which frame and how many frames ago, the latest first. A frame is the one the change's tick fell in, for the last ten minutes of frames. Lines are kept only by a build with Bevy's `track_location`, as every dev build of the sandbox is (`r start` without `--release`, `cargo xtask sandbox`, `play`, `win`) and no release or bench build is; otherwise it gives the frames and a note naming the commands that keep them. A name that matches nothing is told the names it may have meant and the call to make, several of one name their ids (D556); [why.ts](why.ts) writes the answer as those few lines. A body drawn between fixed ticks (`Smoothed`, as the player and every creature and person are) has its `Transform` last written by `terra_world::tick`'s `show`, which draws it there, so its line also says what last moved where it truly stands, in a tick or outside the ticks (a teleport), and on which frame. `node tools/sandbox/whycheck.ts --windows` checks it in play |
| `warp EAST,SOUTH [--facing EAST,SOUTH]` | In play: move the player, as `--warp` does, and wait until they are there |
| `take ITEM[:COUNT] …` | In play: take raw items away, all of a kind if no count (`meat`, `stone:5`), so a test starts from a known pack |
| `unpress` | Let go of every key held or queued by `press` |
| `point X,Y` | Move the pointer to a place in the window, in pixels from its top left, so what is there is hovered |
| `click X,Y [--right] [--frames N]` | Move the pointer there and click, with the left button unless `--right`, held one frame unless `--frames`: what a person's click on a menu's button does |
| `aim EAST,SOUTH [--up m]` | In play: turn the view until its middle, where a bow shoots and a tool reaches, is on a spot so far above the ground (1 m), and wait until it is |
| `give ITEM[:COUNT] …` | In play: carry something, as `--give` does, or set the body (`health:20`), and wait until it is given; fails if it did not fit |
| `pose CLIP [FRACTION]` | In the workbench: hold every model that far through a clip given with `--anim`, or play it |
| `shape [--model N] TEMPLATE` or `shape heavy=0.5 thin=0.2` | In the workbench: reshape a model's body live, as a template or any mix of morphs (`appearance`) |
| `call build.state`, `call build.lay {…}` … | In play: the player's base, read and built through the same checked operations as the hammer: `build.state`, `build.lay`, `build.opening`, `build.fill`, `build.take_apart`, `build.fit`, `build.door`, `build.undo`, `build.op`, `build.point`, `build.look` (the camera in the base's own metres), `build.example` (the castle put up as the base), `build.damage_drawn` (damage drawn or hidden everywhere, for a check), `build.material`, `build.replace`, `build.carve`, `build.take_out`, `build.cube`, `build.ground` (the ground's height under columns, to see what building changed of it), and harm and its mending (D305): `build.damage`, `build.subside`, `build.repair`; what comes down breaks into fragments, counted in `build.state` (see `crates/terra_building/src/remote.rs`), and `build.memory`, what every base holds on the CPU and the GPU |
| `call storage.place {…}`, `storage.put`, `storage.state` | In play: set down an item from the build menu, a chest if none is named, paid for as the hammer pays; put things from the pack into the storage within reach; read the storage in the claim and what each holds (see `crates/terra_survival/src/storage.rs`) |
| `debug.view NAME` | Colour every building by a debug view, its legend on screen, as F4 does in the game: `texels`, `roles`, `detail`, `damage`, `shade`, `normals`, `plan`, `light`, `off`, or `next` and `back` ([development.md](../../docs/development.md#buildings-debug-views)) |
| `tune list [PREFIX]`, `tune get NAME`, `tune set NAME VALUE\|default`, `tune reset [PREFIX]` | The run's tunables (D547, [development.md](../../docs/development.md#tunables)), named numbers its code reads live, such as `sky.cloud.heaped_cover`: a line each with its value, default, range, what set it and what it does; set one within its range (`sky.cloud.heaped_cover: 0.5 -> 0.25 (default 0.5)`, logged as `Tune: …` for `wait`) until the run ends; put changed ones back. `--tune NAME=VALUE` sets one at the start. [tunecheck.ts](tunecheck.ts) checks a value reaches the picture in one running game |
| `menu [open\|close] [--search TEXT] [--page NAME] [--json]` | The debug menu (D81), in a run started with `--debug-menu`: open or close it (the backtick does too, `press backtick`), search its tunables or turn to a page, and say what it shows and where each slider and reset was drawn, in the pixels `click` takes, so a script sets a tunable as a person would; a run without the flag is refused, saying how to start one with it |
| `shot FILE.png` | Save a screenshot and wait for it. If anything has failed to render in the run (a pipeline whose shader did not compile, an error wgpu reported, D555), it says each once as a `✗ render:` line and exits 1, as does every script that shoots through `client.ts`; `call sandbox.shot {"path": …, "frames": N}` saves the next N frames one after another, as `FILE-00000.png` on, to compare frame by frame what a change does as it happens |
| `call METHOD [JSON]` | Any method; `call rpc.discover` lists them, Bevy's `world.*` ones included |

## Scripts

The commands are also a module, [client.ts](client.ts), for scripts that test the game: `start`, `stop`, `press`, `unpress`, `step`, `waitFor`, `waitUntil`, `waitSeconds`, `state`, `warp`, `aim`, `give`, `take`, `hold` and `shot`. Three use it:

- [loop.ts](loop.ts), run by `cargo xtask loop`: the play experiment's loop end to end in one running game, restarted once to load what it saved. Each step sets itself up, aims at what it needs by asking the game where it is, acts, and waits for the game to say what happened. A failing step says what the game said instead and leaves `shots/loop-<step>.png`.
- [cabin.ts](cabin.ts), run by `cargo xtask cabin`: a log cabin on a stone floor from plan to doorway: laid, a doorway and window cut, a roof laid, built step by step from the pack, a cube taken out and the taking undone, a refusal, a plank door and two pairs of shutters fitted, the shut door stopping the player, opened with the interact key, walked through and shut again from inside, a deck a storey up on four posts beside it built and walked up onto by its stairs, stone picked in the hammer for a wall with a cube in it changed to logs and a corner slope on its end, a chest set down and a wall of logs built from the wood stored in it with none carried (D141), saved and loaded the same. Each step checked by `build.state`; screenshots in `shots/cabin-*.png`.
- [rules.ts](rules.ts), run by `cargo xtask rules` after terra_build's rules tests and drawing audit (D257, [research/building-audit.md](../../research/building-audit.md)): every building rule checked live by state in an optimised build: nothing built in the air, off an unbuilt post or off an overhang into nothing; nothing taken from under a cube or an eave, carved, changed or taken out from under what it holds; nothing outside the claim, where the player stands or through the claim stone; a post stops the player at its width and an underside at head height stops them under it; a slate hip built and pictured half up and done (`shots/rules-*.png`); a cube's edit timed to the screen (`Build: change on screen`), and the worst frames while building and walking the village's street (`sandbox.frames`).
- [demo.ts](demo.ts), run by `cargo xtask demo [--skip-cabin] [--hour 15]`: the construction demo's pictures, the same every time. It runs the cabin script, loads the game it saved, sets the player at the end of the village's street and takes the camera round fixed views: the street at eye height, the green, the street from its east end, the village from a rise and from above, every building of the village close up, a stone house going up beside the cabin with the rest of it ghosts, and the cabin. The village logs where to stand for its views (`Settlement vantage: …`, `Settlement: …: its door …`), so they follow it wherever its seed sets it down. The hour is set before each picture with the clock running. Pictures in `shots/demo/NN-<view>.png`, and a sheet of them where ImageMagick is installed.
- [places.ts](places.ts): the table of places (D326), each with the sandbox options that put the camera there, its fixed views, the reference it is held to and its route: `lush`, the lush forest, and `lake`, the mountain lake (docs/demos.md §1). `vantage.ts` and `film.ts` take `--place <name>`, `lush` by default.
- [vantage.ts](vantage.ts), run by `cargo xtask vantage [--place lake] [--time 13,17] [--date 10-15]` (`--date` for a day of the year, docs/climate.md): the vantage sheet ([docs/biomes.md](../../docs/biomes.md#how-wed-know-d69)), the lush forest from fixed views (its floor at eye height, its edge, the clearing, an overlook) at each hour asked for, side by side in `shots/vantage/sheet.jpg`, so a change to how the world looks is judged on the same views; and, at the first hour, how closed the canopy is: the share of sky looking straight up from eye height at twelve places through the forest, its mean and median (D245). For the views inside the forest it prints how each looks against Sons of the Forest's own daytime forest frames (the reference `looks/sotf-forest-day.json`; any frames or film can be measured against any reference with `node tools/sandbox/look.ts measure [--against <name>] [--player] <files>`, and a reference made from frames with `node tools/sandbox/look.ts reference <name> --about "…" [--open] <files>`, its pictures kept outside the repository; a reference of open views made `--open` is measured by band too, the sky, the far land under the skyline, the middle distance and the near ground, with how far the far land stands under the sky and how much bluer it is than the middle (D326), and `--draw-bands <dir>` draws where the bands fell), measured as [research/2026-10-14-sotf-forest-look.md](../../research/2026-10-14-sotf-forest-look.md) measured them: mean brightness, the darkest twentieth, the share below 0.08, red and blue against green, local contrast and lit litter in the lower third ([look.ts](look.ts), checked by [look.test.ts](look.test.ts); D286). One scripted run an hour, about ten seconds each, moving its camera from view to view (`--vantage …@frame`) and saving each with `--shots`.
- [looks.ts](looks.ts), run by `cargo xtask looks [--place lush|lake|tundra|town|all] [--time 13] [--from <dir>]`: the looks check (D356), each place's measured views shot (vantage.ts's `shootViews`) and held to the art style's rules for places ([docs/art-style.md](../../docs/art-style.md#places)): a table a place of each number [style.json](style.json) holds, the views' mean, the reference's number and its tolerance, ok or FAIL, and the view furthest out, then what is furthest out across places; it exits 1 when a number does not hold. `--from` measures `<hour>-<view>.png` already shot. Each view is shot again six frames on with the lakes drawn flat magenta (`--water-mask`), saved beside it as `<hour>-<view>.water.png`; the debug-tint rule leaves the water it marks out of its fills, by what draws it rather than its colour (D429). Its measures beyond D286's, debug tint and lilac, hard shade edges, facet edges, flat colour and flat foliage (leaf colour spread and leaves catching the light, D368), are look.ts's, tested on made-up pictures; the judging and the style file's consistency with the places, references and guide by [looks.test.ts](looks.test.ts).
- [flightplot.ts](flightplot.ts), run by `node tools/sandbox/flightplot.ts <scene> <out.png>`: a trailer scene's flier course plotted before it is filmed (D382), as `terra_creatures::fliers` flies it ([trailer/flight.ts](trailer/flight.ts) works its plan out the same way): from above coloured by speed with a dot a second, and through the film its height, speed, the bank its turns ask, its climb and how far it is off the camera's aim, orange where it breathes fire; each breath cast from the mouth into the scene's building (`cargo run -p terra_build_scenes --example rays`), red where it strikes and grey where it misses, the building's footprint under the course, and each breath said on the terminal: how many of its aims strike, how far from the mouth, and how far off the way. The `flight` scene (`--cut tools/sandbox/trailer/flight.json`) films a dragon's moves over the meadow, to judge how it flies.
- [collide.ts](collide.ts), run by `cargo xtask collide [--count 20]`: walks the player into what stands in the lush forest and checks, against the meshes themselves rather than the shapes fitted to them, that what stops them is what they see (D267). Every thing with a footing is listed (`lush.solids`), so a kind added later is tried too, and the seven kinds the forest must have (`Rock`, `Boulder`, `Stump`, `Log`, `Oak`, `Pine`, `Spruce`) must be there and fitted. Of each kind, low and tall ones, and logs' low ends walked across; for each the player is set down 4 m off with nothing else in the way to it nor, for a low thing, past it where they step down ([ways.ts](ways.ts)), and must stay where they were put (not pushed out of a spruce's skirt), at a different turn round it each time, and walks at it for 110 frames, every frame recorded; one with no such way gives its place to the next nearest of its kind. It fails when the body stood more than 0.1 m into a mesh taller than a step, was stopped more than 0.35 m short of a tall thing as drawn (an invisible wall), did not step over a thing under 0.35 m, or was lifted more than a step onto something taller. Pictures in `shots/collide/`. About a minute and a half, on a release build. `world.obstacles {at, within}` answers what stops a walker near a spot (`world.solids {at, within}`, each one's pieces in the world's frame, for a fixture), `world.fell {at, within, taller_than?}` fells the trees within so far of a spot (those taller than so many metres), as a scene clears woods round a set piece, `lush.footprint {points, thing?, lifts?}` how far spots are from the meshes (of anything, and of anything but `thing`; given each spot's feet over the ground, only what of a mesh stands over those feet), and where the player has been since it was last asked.
- [artifacts.ts](artifacts.ts), run by `cargo xtask artifacts --frames [--quality high,low] [--checks still,sun,glide,going-up,undamaged,damaged]`: building's junk that only frames show, on the GPU at each preset ([docs/building-drawing.md](../../docs/building-drawing.md)): views held still with the clock stopped (anything changing is noise: acne, crawl, mip shimmer), the sun moving over a still view (acne, cascades), a camera gliding down the town's street (a pixel flipping for a frame), a stone house going up from outside and inside (flashes while sections are laid again, TAA trailing a new piece, a light probe popping as its room closes), houses never harmed (no damage drawn on them) and houses harmed (their timber's and roofs' damage holding still and showing). Frames are read and compared in Node ([png.ts](png.ts), [frames.ts](frames.ts), whose measures [frames.test.ts](frames.test.ts) checks against planted faults); each check's worst frame is saved with what changed marked red in `shots/artifacts/<preset>/sheet/`. About ten minutes a preset.
- [lodcheck.ts](lodcheck.ts), run by `cargo xtask lodcheck [--views floor,path,clearing,village,town] [--time 17] [--limit 0.5]`: what pops as levels of detail change, without camera motion to confuse it, in the lush forest, the bench's fifty buildings on the yard (`village`) and down a street of forty buildings (`town`, D278); and a view whose last frame is over 1% black. Under WSL each view runs on the Windows build, on the real GPU, since WSL's own draws on the CPU too slowly to finish. Each view is held still with the clock and wind stopped while every switch distance in the world is swept from half to twice its own (`--detail-sweep`), so every crown, trunk, shadow and grass ring crosses its switch in front of a still camera. Each pair of frames is differenced at half size and opened morphologically, so a crossfade's scattered pixels vanish and a patch that appears or goes at once survives. Prints each view's worst frames with the share that popped and the scale it popped at, marks them red in `shots/lodcheck/sheet.jpg`, and fails if any frame pops more than the limit. About 40 s a view. Checked against crossfades turned off, which it fails three times over.
- [popin.ts](popin.ts), run by `node tools/sandbox/popin.ts <film.mp4 | frames directory> [--out dir] [--least 12]`: what appears whole inside the picture between frames of a film or still sequence already made, an animal put out in view most of all (docs/scene-rules.md, Appearance). A pixel is new when it is brighter or darker than anything within 5 px (at 480x270) of it in the two frames before, and stays the next two; a patch of new pixels not touching the picture's edge is a pop-in. Cuts and flames are passed over. Prints each with its time and place, marks the largest in `<out>/popin-<frame>.jpg`, and exits 1 if any. About a minute for 20 s at 30 fps. A 40x24 px patch planted into the lake film's r12 is caught; the same faded in over 0.6 s is not.
- [groundlight.ts](groundlight.ts), a continuous check (`tools/continuous/checks.json`): the yard at night from a fixed camera beside where a campfire will stand, shot before it is staged and once it burns, through the GPU scheduler on a release build; the ground within the hearth light's reach must brighten against ground beyond it, in linear light, and the ring's firelit stones must read orange (hue 20-40°, saturation at least 0.6), not salmon pink, or it exits 1. `--from <dir>` measures a run already made.
- [indoorlight.ts](indoorlight.ts), a continuous check (`tools/continuous/checks.json`; D485, D486): the crypt of `--experiment dungeon` from its first room and a torch-lit corridor at noon and at midnight, through the GPU scheduler on a release build; inside, each view's mean brightness must be the same by day and night within 10% and its darkest twentieth under 0.02, or it exits 1; a forest view from the same run is reported beside them. `--from <dir>` measures a run already made (`noon-00090.png`, ...).
- [pops.ts](pops.ts), run by `cargo xtask pops [--frames 1200-1320] [-- sandbox options]`: what pops in or out, or flickers for a frame, in a stretch of a scripted run, by default the bench's walk through the lush forest at 17:00. It saves consecutive frames with `--shots` and compares each with the ones either side, small and blurred so the camera's smooth motion cancels: a pop changes a frame from the one before but not into the one after, a flicker from both neighbours, which agree. Prints each frame's share that popped and flickered, and puts the worst beside where it happened, marked red, in `shots/pops/pops.jpg`. A planted 20-pixel patch scores about 1%; a smooth walk under 0.2%. Leaves brushing the camera score high too.
- [trailer.ts](trailer.ts), run by `cargo xtask trailer [--only lake,forest] [--again] [--stills] [--no-render] [--size 1920x1080]`: the trailer ([docs/trailer.md](../../docs/trailer.md), D357). Each run in [trailer/runs/](trailer/runs) (a place of `places.ts`, its hour and date, the player's route, its sound) is filmed in the play experiment with the game's own camera following, the route smoothed into a spot every 4 m ([timeline.ts](timeline.ts), checked by [timeline.test.ts](timeline.test.ts)), with the look `--cine` gives it (the exposure and clock held, motion blur), every second frame of a run stepped at 60 kept for 30 fps; letterboxed and left with its own sound bed (`terra_sandbox --sound-bed`, the game's code-made sounds and music) as `~/.cache/terra-review/trailer/<name>.mp4`; then [trailer/cut.json](trailer/cut.json)'s runs are crossfaded between a title and an end card into `cut.mp4`, with a contact sheet. It builds the release sandbox first (a no-op when it is fresh, a line when it was rebuilt), so a film of new code never runs an old binary. A run newer than its shot file, its scene and the sandbox is kept. `--stills` saves only each run's first, middle and last frame on one sheet, to judge a route in a minute. ## What the run said, and the mark

Everything the log keeps is also kept in memory, numbered, with the frame it was said on (`crates/terra_world/src/record.rs`), so a script can ask what happened instead of counting frames. Every on-screen notice is logged, as are kills, gains, things made and much else, so most checks need no new code: act, then `wait` for the words.

The client keeps a mark in `shots/remote.mark`: the first line not yet looked at. Commands that act (`press`, `step`, `warp`, `give`) move it to now before acting, so `wait` and `said` see only what followed; `wait` moves it past what it found, so waiting twice for the same words waits for them twice. When `wait` times out it prints what was said instead, which is usually the reason.

When a check needs a fact the log does not say, add it to `play.state` (`crates/terra_game/src/play/probe.rs`) rather than parsing the screen: one place that answers what is true, read the same way by every test.

Changes made this way last only as long as the run. When a value is right, put it where it belongs (a socket's place goes in `tools/characters/export_character.py`, a tunable's default in its owner's code), and check it with a workbench sheet.

## How it reaches the sandbox

The sandbox listens on `localhost:15702`, or the port `--remote-port` gives. Under WSL, a sandbox running on Windows is on Windows' own localhost, which WSL cannot reach, so the client sends through Windows' `curl.exe` there, and writes screenshots through WSL's share so they land where you asked. The remote protocol can change anything in the running world, so it only listens on localhost and only when started with `--remote`.

To add a method, see `crates/terra_world/src/remote.rs`: an experiment registers its own with `remote::method`, as the workbench does with `workbench.pose` and play with `play.state`. A method that changes the game asks for it and lets the system that already does the same for the command line do it on the next frame, as `play.warp` does with `--warp`, so the two cannot drift apart; it logs what it did, so the client can wait for that. An experiment that moves its camera in `PostUpdate` orders that `.before(remote::CameraHold)`, so a held camera wins and what it sees is not culled from the old view.
