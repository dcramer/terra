# Sandbox remote

Drives a running sandbox from the command line over Bevy's remote protocol (D69): find things, move them, hold the camera on them, pause and step the clock, press keys, read what is true and what the run has said, wait for something to happen, pose a model, and take screenshots, all without restarting. Use it whenever you would otherwise change a number and restart to see the result, such as placing a socket, fitting gear or framing a shot, and to test a feature in one running game instead of a scripted run per step. TypeScript, run directly by Node 22.18 or later, with no dependencies.

```bash
r() { node tools/sandbox/remote.ts "$@"; }

r start --windows -- --experiment workbench --model models/character/base.glb --hold stone_axe --anim Walk_Loop
r find socket.hand                       # names containing it, with where they are
r pose Walk_Loop 0.6                     # every model held 60% through the walk
r shape --model 0 heavy=0.5 strong=0.3   # the first model's body, half heavy and a little strong
r look socket.hand.R --distance 0.9 --around 90
r place socket.hand.R --rotation 70,0,0  # its local transform; rotation in degrees
r shot shots/hand.png                    # waits for the file
r stop
```

Testing a feature in play, in one running game:

```bash
r start --windows -- --experiment play --fresh --save test.ron
r give bow quiver arrow:4                # waits until each is given
r warp -32,34 --facing -45,36            # waits until the player is there
r state                                  # where they are, their body, what they carry, what is near
r aim -45,36 --up 0.8                    # the middle of the view on the deer's chest
r press 5 e@10:60                        # the bow, then ten frames later draw for 60 and loose
r wait "An arrow hit" --timeout 20       # or fail, showing what was said instead
r said                                   # everything said since the last action
```

`start` runs the sandbox in the background on a port nothing else answers on, records the port in `shots/remote.port`, and waits until it answers; every other command talks only to that port, so commands never reach a sandbox another session is driving (`TERRA_REMOTE_PORT` overrides it); anything after `--` goes to the sandbox, and `--windows` runs it on the Windows GPU from WSL (`cargo xtask win`), which is much faster than WSL's CPU renderer. Its log is `shots/remote.log`. A sandbox started by hand with `--remote` works the same. `start` also passes `--steady`, so the game moves a sixtieth of a second every frame however fast frames are drawn, as scripted runs do: a key held for 60 frames is a second of play on any machine. `--real-time` leaves the clock alone. It passes `--background` too, so the run stays out of the way of whoever is at the machine: its window opens behind the others without taking focus, never takes the mouse, ignores the real keyboard and mouse, and is silent; only the script drives it. `--foreground` gives a normal window, to play alongside the script.

| Command | What it does |
|---|---|
| `start [--windows] [--real-time] [--foreground] [-- options]` | Start a sandbox listening, and wait for it |
| `stop` | Close it |
| `find NAME` | Entities whose name contains NAME: id, where they are, their local transform |
| `place NAME [--translation x,y,z] [--rotation x,y,z] [--scale s]` | Set the local transform of the entity called exactly NAME |
| `look NAME\|x,y,z [--distance m] [--around degrees] [--height m] [--aim m] [--from x,y,z]`, `look --vantage x,y,z,x,y,z` | Hold the camera on an entity, following it, or a point; `around` is from the model's front, `aim` how far above it to look (a person's position is their feet); `from` puts the eye at a point in the world; `--vantage`, as the sandbox's option and the kit sheet's log give it, an eye and what it looks at from the start |
| `release` | Let the camera go |
| `pause`, `resume` | Stop and start the game's clock, animations included |
| `step FRAMES` | Stop the clock, let it run that many frames, stop it again, and wait until it has |
| `press KEY[@AFTER][:FRAMES] …` | Hold keys, named as `--press` names them, for so many frames (one if not given), starting so many frames from now (none if not given): `e`, `w:60`, `f@40`, `e@90:80`. A sequence of keys goes in one command, timed against the game's frames rather than the script's |
| `status` | The frame, the game's time, whether the clock is stopped, whether the loading screen is up, and the next line's number |
| `call sandbox.frames {"seconds": 10}` | How the frames of the last so many seconds went on the real clock: median, 99th percentile and worst of the time between frames, their work, the game's update and the GPU's, to time a stretch of play |
| `said [--containing TEXT] [--all] [--from LINE]` | What the run has said since the mark, with the frame of each |
| `wait TEXT [--timeout s]` | Wait until the run says something containing TEXT since the mark; on timeout, show what it said instead and fail |
| `mark` | Start `said` and `wait` from now |
| `state` | In play: where the player is and faces, their body, what they hold, carry and wear, and the creatures and people within 40 m |
| `warp EAST,SOUTH [--facing EAST,SOUTH]` | In play: move the player, as `--warp` does, and wait until they are there |
| `take ITEM[:COUNT] …` | In play: take raw items away, all of a kind if no count (`meat`, `stone:5`), so a test starts from a known pack |
| `unpress` | Let go of every key held or queued by `press` |
| `point X,Y` | Move the pointer to a place in the window, in pixels from its top left, so what is there is hovered |
| `click X,Y [--right] [--frames N]` | Move the pointer there and click, with the left button unless `--right`, held one frame unless `--frames`: what a person's click on a menu's button does |
| `aim EAST,SOUTH [--up m]` | In play: turn the view until its middle, where a bow shoots and a tool reaches, is on a spot so far above the ground (1 m), and wait until it is |
| `give ITEM[:COUNT] …` | In play: carry something, as `--give` does, or set the body (`health:20`), and wait until it is given; fails if it did not fit |
| `pose CLIP [FRACTION]` | In the workbench: hold every model that far through a clip given with `--anim`, or play it |
| `shape [--model N] TEMPLATE` or `shape heavy=0.5 thin=0.2` | In the workbench: reshape a model's body live, as a template or any mix of morphs (`appearance`) |
| `call build.state`, `call build.lay {…}` … | In play: the player's base, read and built through the same checked operations as the hammer: `build.state`, `build.lay`, `build.opening`, `build.fill`, `build.take_apart`, `build.fit`, `build.door`, `build.undo`, `build.op`, `build.point`, `build.look` (the camera in the base's own metres), `build.example` (the castle put up as the base), `build.damage_drawn` (damage drawn or hidden everywhere, for a check), `build.material`, `build.replace`, `build.carve`, `build.take_out`, `build.cube`, and harm and its mending (D305): `build.damage`, `build.subside`, `build.repair`; what comes down breaks into fragments, counted in `build.state` (see `crates/terra_game/src/build/remote.rs`), and `build.memory`, what every base holds on the CPU and the GPU |
| `call storage.place {…}`, `storage.put`, `storage.state` | In play: set down an item from the build menu, a chest if none is named, paid for as the hammer pays; put things from the pack into the storage within reach; read the storage in the claim and what each holds (see `crates/terra_game/src/play/storage.rs`) |
| `shot FILE.png` | Save a screenshot and wait for it; `call sandbox.shot {"path": …, "frames": N}` saves the next N frames one after another, as `FILE-00000.png` on, to compare frame by frame what a change does as it happens |
| `call METHOD [JSON]` | Any method; `call rpc.discover` lists them, Bevy's `world.*` ones included |

## Scripts

The commands are also a module, [client.ts](client.ts), for scripts that test the game: `start`, `stop`, `press`, `unpress`, `step`, `waitFor`, `waitUntil`, `waitSeconds`, `state`, `warp`, `aim`, `give`, `take`, `hold` and `shot`. Three use it:

- [loop.ts](loop.ts), run by `cargo xtask loop`: the play experiment's loop end to end in one running game, restarted once to load what it saved. Each step sets itself up, aims at what it needs by asking the game where it is, acts, and waits for the game to say what happened. A failing step says what the game said instead and leaves `shots/loop-<step>.png`.
- [cabin.ts](cabin.ts), run by `cargo xtask cabin`: a log cabin on a stone floor from plan to doorway: laid, a doorway and window cut, a roof laid, built step by step from the pack, a cube taken out and the taking undone, a refusal, a plank door and two pairs of shutters fitted, the shut door stopping the player, opened with the interact key, walked through and shut again from inside, a deck a storey up on four posts beside it built and walked up onto by its stairs, stone picked in the hammer for a wall with a cube in it changed to logs and a corner slope on its end, a chest set down and a wall of logs built from the wood stored in it with none carried (D141), saved and loaded the same. Each step checked by `build.state`; screenshots in `shots/cabin-*.png`.
- [rules.ts](rules.ts), run by `cargo xtask rules` after terra_build's rules tests and drawing audit (D257, [research/building-audit.md](../../research/building-audit.md)): every building rule checked live by state in an optimised build: nothing built in the air, off an unbuilt post or off an overhang into nothing; nothing taken from under a cube or an eave, carved, changed or taken out from under what it holds; nothing outside the claim, where the player stands or through the claim stone; a post stops the player at its width and an underside at head height stops them under it; a slate hip built and pictured half up and done (`shots/rules-*.png`); a cube's edit timed to the screen (`Build: change on screen`), and the worst frames while building and walking the village's street (`sandbox.frames`).
- [demo.ts](demo.ts), run by `cargo xtask demo [--skip-cabin] [--hour 15]`: the construction demo's pictures, the same every time. It runs the cabin script, loads the game it saved, sets the player at the end of the village's street and takes the camera round fixed views: the street at eye height, the green, the street from its east end, the village from a rise and from above, every building of the village close up, a stone house going up beside the cabin with the rest of it ghosts, and the cabin. The village logs where to stand for its views (`Settlement vantage: …`, `Settlement: …: its door …`), so they follow it wherever its seed sets it down. The hour is set before each picture with the clock running. Pictures in `shots/demo/NN-<view>.png`, and a sheet of them where ImageMagick is installed.
- [places.ts](places.ts): the table of places (D326), each with the sandbox options that put the camera there, its fixed views, the reference it is held to and its route: `lush`, the lush forest, and `lake`, the mountain lake (docs/demos.md §1). `vantage.ts` and `film.ts` take `--place <name>`, `lush` by default.
- [vantage.ts](vantage.ts), run by `cargo xtask vantage [--place lake] [--time 13,17] [--date 10-15]` (`--date` for a day of the year, docs/climate.md): the vantage sheet ([docs/biomes.md](../../docs/biomes.md#how-wed-know-d69)), the lush forest from fixed views (its floor at eye height, its edge, the clearing, an overlook) at each hour asked for, side by side in `shots/vantage/sheet.jpg`, so a change to how the world looks is judged on the same views; and, at the first hour, how closed the canopy is: the share of sky looking straight up from eye height at twelve places through the forest, its mean and median (D245). For the views inside the forest it prints how each looks against Sons of the Forest's own daytime forest frames (the reference `looks/sotf-forest-day.json`; any frames or film can be measured against any reference with `node tools/sandbox/look.ts measure [--against <name>] [--player] <files>`, and a reference made from frames with `node tools/sandbox/look.ts reference <name> --about "…" [--open] <files>`, its pictures kept outside the repository; a reference of open views made `--open` is measured by band too, the sky, the far land under the skyline, the middle distance and the near ground, with how far the far land stands under the sky and how much bluer it is than the middle (D326), and `--draw-bands <dir>` draws where the bands fell), measured as [research/2026-10-14-sotf-forest-look.md](../../research/2026-10-14-sotf-forest-look.md) measured them: mean brightness, the darkest twentieth, the share below 0.08, red and blue against green, local contrast and lit litter in the lower third ([look.ts](look.ts), checked by [look.test.ts](look.test.ts); D286). One scripted run an hour, about ten seconds each, moving its camera from view to view (`--vantage …@frame`) and saving each with `--shots`.
- [collide.ts](collide.ts), run by `cargo xtask collide [--count 20]`: walks the player into what stands in the lush forest and checks, against the meshes themselves rather than the shapes fitted to them, that what stops them is what they see (D267). Every thing with a footing is listed (`lush.solids`), so a kind added later is tried too, and the seven kinds the forest must have (`Rock`, `Boulder`, `Stump`, `Log`, `Oak`, `Pine`, `Spruce`) must be there and fitted. Of each kind, low and tall ones, and logs' low ends walked across; for each the player is set down 4 m off with nothing else in the way to it nor, for a low thing, past it where they step down ([ways.ts](ways.ts)), and must stay where they were put (not pushed out of a spruce's skirt), at a different turn round it each time, and walks at it for 110 frames, every frame recorded; one with no such way gives its place to the next nearest of its kind. It fails when the body stood more than 0.1 m into a mesh taller than a step, was stopped more than 0.35 m short of a tall thing as drawn (an invisible wall), did not step over a thing under 0.35 m, or was lifted more than a step onto something taller. Pictures in `shots/collide/`. About a minute and a half, on a release build. `world.obstacles {at, within}` answers what stops a walker near a spot, `lush.footprint {points, thing?}` how far spots are from the meshes (of anything, and of anything but `thing`), and where the player has been since it was last asked.
- [artifacts.ts](artifacts.ts), run by `cargo xtask artifacts --frames [--quality high,low] [--checks still,sun,glide,going-up,undamaged]`: building's junk that only frames show, on the GPU at each preset ([docs/building-drawing.md](../../docs/building-drawing.md)): views held still with the clock stopped (anything changing is noise: acne, crawl, mip shimmer), the sun moving over a still view (acne, cascades), a camera gliding down the town's street (a pixel flipping for a frame), and a stone house going up from outside and inside (flashes while sections are laid again, TAA trailing a new piece, a light probe popping as its room closes). Frames are read and compared in Node ([png.ts](png.ts), [frames.ts](frames.ts), whose measures [frames.test.ts](frames.test.ts) checks against planted faults); each check's worst frame is saved with what changed marked red in `shots/artifacts/<preset>/sheet/`. About ten minutes a preset.
- [lodcheck.ts](lodcheck.ts), run by `cargo xtask lodcheck [--views floor,path,clearing,village,town] [--time 17] [--limit 0.5]`: what pops as levels of detail change, without camera motion to confuse it, in the lush forest, the bench's fifty buildings on the yard (`village`) and down a street of forty buildings (`town`, D278); and a view whose last frame is over 1% black. Under WSL each view runs on the Windows build, on the real GPU, since WSL's own draws on the CPU too slowly to finish. Each view is held still with the clock and wind stopped while every switch distance in the world is swept from half to twice its own (`--detail-sweep`), so every crown, trunk, shadow and grass ring crosses its switch in front of a still camera. Each pair of frames is differenced at half size and opened morphologically, so a crossfade's scattered pixels vanish and a patch that appears or goes at once survives. Prints each view's worst frames with the share that popped and the scale it popped at, marks them red in `shots/lodcheck/sheet.jpg`, and fails if any frame pops more than the limit. About 40 s a view. Checked against crossfades turned off, which it fails three times over.
- [pops.ts](pops.ts), run by `cargo xtask pops [--frames 1200-1320] [-- sandbox options]`: what pops in or out, or flickers for a frame, in a stretch of a scripted run, by default the bench's walk through the lush forest at 17:00. It saves consecutive frames with `--shots` and compares each with the ones either side, small and blurred so the camera's smooth motion cancels: a pop changes a frame from the one before but not into the one after, a flicker from both neighbours, which agree. Prints each frame's share that popped and flickered, and puts the worst beside where it happened, marked red, in `shots/pops/pops.jpg`. A planted 20-pixel patch scores about 1%; a smooth walk under 0.2%. Leaves brushing the camera score high too.
- [film.ts](film.ts), run by `cargo xtask film [--place lake] [--frames 300-2700] [--time 15] [--date 10-15] [-- sandbox options]`: a video of a scripted run, by default the bench's 40-second walk through the lush forest, with `--place` that place's route, to see how the world looks and moves. Every second frame is saved with `--shots …/2` and put together by ffmpeg at 30 frames a second, so it plays at the game's speed however slowly it was drawn; `shots/film.mp4`, about 4 MB a second at 1080p. Needs ffmpeg.
- [qa.ts](qa.ts), run by `cargo xtask qa clips|<scenario> [--set <kit>|mixes|all] [--part <stage>] [--no-trace]`: QA clips for people to watch, the same every time, of building and destruction in a set of kits, each 10 to 30 s of one stage from one or two fixed cameras, its caption saying what to look for. `clips` makes every clip: [`build-walls`](qa/build-walls.ts) (footings and walls rising), [`build-openings`](qa/build-openings.ts) (a window cut and shuttered, a door fitted and opened), [`build-roof`](qa/build-roof.ts) (the roof through its four stages), [`build-swap`](qa/build-swap.ts) (a wall's material changed in place), [`build-carve`](qa/build-carve.ts) (a window carved), [`build-storey`](qa/build-storey.ts) (the roof off, a storey on, a roof again: nothing but a roof is built on a roof's cubes), [`build-deck`](qa/build-deck.ts) (a deck on posts and its stairs) and [`destroy`](qa/destroy.ts) (a finished house brought down by knocking out its ground course, fragments falling, settling and fading). Each puts its cabin up as far as it needs at once and unfilmed ([qa/lib/cabin.ts](qa/lib/cabin.ts)), then films its stage. Other scenarios run by name: [`film`](qa/film.ts) (the whole cabin as one long film), [`harm`](qa/harm.ts) (cracks, a wall's foot, a roof losing its walls, a tower, the ground giving way, mending), [`materials`](qa/materials.ts), [`shapes`](qa/shapes.ts) and [`castle`](qa/castle.ts) (edits to the 140,000-cube castle, put up as the base with `build.example`, timed to the screen). A scenario is a file of sandbox options and a timeline of remote calls on given frames and camera moves, written against a set ([qa/script.ts](qa/script.ts)); a set is a wall kit with its roof, `all` the building baseline's (D333: the materials `assets/data/settlement.ron` builds in) and `mixes`, every baseline kit meeting; a frozen kit is filmed by name. Building costs nothing (`--free-build`). Each clip runs three times on the Windows GPU: a first pass live over the remote, to learn how many steps each fill takes and to fail on any refusal the scenario does not expect (`allow`); the film, a scripted run making the calls on their frames (`--calls`) with every section laid before each frame is drawn, every second frame joined by ffmpeg at the game's speed with its caption, in `shots/qa/<scenario>/<set>.mp4` and a 720p copy (`<set>-720p.mp4`), and a contact sheet, `<set>.jpg`; and the trace, the same calls in a benchmark run laying on the workers as play does, every frame's time in `<set>-frames.csv` and, in `<set>.txt`, the frames against the 13.3 ms budget (D25), each edit's time to the screen, changes shown torn, and the worst frames beside what was done on them, with the machine's load. A camera move within 40 cm of a building's box (`solid`) is said before it is filmed. `--first` makes only the first pass, with a picture at the end of each stage in `first-<set>/` and, with `--answers`, every call's answer: what a scenario is written by. `shots/qa/index.html` has a row a set, each clip's sheet linking to its film beside its p99 against the budget. About three minutes a clip.
- [diverge.ts](diverge.ts): where two runs of the game part ways. The sandbox writes the play experiment's whole state every frame with `--trace FILE.jsonl`; `diverge.ts A.jsonl B.jsonl` names the first frame that differs and the values that differ in it. `diverge.ts --twice -- <options for a scripted run>` runs the same run twice and compares, which says whether the game does the same thing from the same start and keys.

## What the run said, and the mark

Everything the log keeps is also kept in memory, numbered, with the frame it was said on (`crates/terra_world/src/record.rs`), so a script can ask what happened instead of counting frames. Every on-screen notice is logged, as are kills, gains, things made and much else, so most checks need no new code: act, then `wait` for the words.

The client keeps a mark in `shots/remote.mark`: the first line not yet looked at. Commands that act (`press`, `step`, `warp`, `give`) move it to now before acting, so `wait` and `said` see only what followed; `wait` moves it past what it found, so waiting twice for the same words waits for them twice. When `wait` times out it prints what was said instead, which is usually the reason.

When a check needs a fact the log does not say, add it to `play.state` (`crates/terra_game/src/play/probe.rs`) rather than parsing the screen: one place that answers what is true, read the same way by every test.

Changes made this way last only as long as the run. When a value is right, put it where it belongs (a socket's place goes in `tools/characters/export_character.py`), and check it with a workbench sheet.

## How it reaches the sandbox

The sandbox listens on `localhost:15702`, or the port `--remote-port` gives. Under WSL, a sandbox running on Windows is on Windows' own localhost, which WSL cannot reach, so the client sends through Windows' `curl.exe` there, and writes screenshots through WSL's share so they land where you asked. The remote protocol can change anything in the running world, so it only listens on localhost and only when started with `--remote`.

To add a method, see `crates/terra_world/src/remote.rs`: an experiment registers its own with `remote::method`, as the workbench does with `workbench.pose` and play with `play.state`. A method that changes the game asks for it and lets the system that already does the same for the command line do it on the next frame, as `play.warp` does with `--warp`, so the two cannot drift apart; it logs what it did, so the client can wait for that. An experiment that moves its camera in `PostUpdate` orders that `.before(remote::CameraHold)`, so a held camera wins and what it sees is not culled from the old view.
